# predel

Платформа подбора ИТ-специалистов с подтверждением специализации и грейда через опрос и тестирование. Работодатель описывает потребность, находит кандидатов и отправляет персональное приглашение с зарплатной вилкой; публикация вакансии для этого не требуется.

## Текущий статус

Главная страница сохраняет дизайн из предоставленного архива: плавающую шапку, синий акцент, изображение брелоков и исходную композицию. «Попробовать» открывает регистрацию; кабинет, подбор, профили, тестирование и приглашения доступны после подтверждения почты и входа. Прямая ссылка на кабинет также требует регистрации. Иллюстрации на главной обозначены как примеры интерфейса. Внизу сайта размещены логотипы из шаблона презентации ФСП.

В разделе кандидата «Найти компании» доступен «Предельный режим»: каждое открытое предложение показывается отдельной карточкой с компанией, задачами, зарплатой и условиями. Свайп влево пропускает предложение, вправо открывает форму отклика; доступны кнопки, стрелки на клавиатуре и возврат предыдущей карточки. Отклик отправляется после подтверждения в форме. Режим сохраняется при обновлении страницы, просмотренные карточки можно открыть снова. Проверка режима: `npm run test:offers` при работающем сервисе.

Новый кандидат начинает с анкеты: отрасль, роль, специализация, самооценка грейда, стек и опыт. Общий стаж и места работы с задачами показаны отдельно. Если итог не написан в резюме, стаж рассчитывается по периодам работы; пересекающиеся месяцы учитываются один раз. Неверные периоды остаются в истории, но исключаются из расчёта с предупреждением; даты только с годами дают верхнюю оценку. Софт-скиллы заполняются вручную или импортируются из резюме, сохраняются в анкете и показываются как самооценка; выбирать их необязательно. После анкеты кандидат проходит тест; подтверждённая категория появляется только при успешной серверной попытке. В каталоге 146 вымышленных демонстрационных профилей; их результаты тестов и достижения явно помечены как демонстрационные.

В анкете 14 специализаций: Frontend, Backend, Fullstack, мобильная разработка, ML и Data Science, аналитика и инженерия данных, DevOps/SRE, тестирование, информационная безопасность, UX/UI, бизнес и системный анализ, управление продуктом, Embedded и электроника. Для каждой есть отдельные программы пяти грейдов: Стажёр, Junior, Middle, Senior, Lead. Доступны 25 отраслей; списки одинаковы в анкете, профиле и поиске. Импорт резюме распознаёт явно указанную роль и грейд, а стек фильтров подбора учитывает выбранное направление. Стаж сам по себе не назначает грейд.

«Прикрепить резюме» заполняет анкету из PDF, DOCX, текста или изображения. Сначала читается текст документа; для сканов работает локальный OCR на русском и английском. Страницы с крупными растровыми изображениями распознаются даже при наличии текстового слоя, чтобы неполная шапка не скрывала остальной опыт. Кандидат проверяет результат, дополняет недостающие сведения и отдельно даёт согласие. Достижения, образование, проекты, языки и портфолио сохраняются в профиле. [Требования и приватность](docs/resume_requirements.md).

Объединена ветка `feature/resume-conversion`: опыт работы и личные проекты извлекаются раздельно, даты проектов не увеличивают стаж. Проекты сохраняются совместимым текстом вместе с историей работы, интересы и дополнительные сведения — в «О себе». Структуры парсера пока не являются отдельными сущностями базы. Подсказки ролей и расширенные софт-скиллы используют общий справочник; дополнительные навыки раскрываются по запросу. Распознавание остаётся эвристическим, поля требуют проверки кандидатом.

Кабинет показывает доступную историю анкет и тестов со связанными сведениями. PDF-профиль генерируется локально и скачивается файлом, включая только разрешённые контакты. Изоляция демо отделяет гостевой учебный каталог от зарегистрированных профилей. Историческую анкету пока можно заменить через API под прежним ID; подтверждённые результаты теста при этом остаются серверными.

Импорт проверен на четырёх предоставленных PDF, изображении страницы резюме и синтетических PDF/DOCX/сканах. [Фактические результаты](docs/resume_validation.md).

Тесты формирует и проверяет Node.js API: ключи ответов отсутствуют в браузере, попытки и результаты сохраняются в серверной SQLite. В блоке «По вакансии» можно выбрать пример своей программы или вставить своё описание; структура программы сохраняется, показываются непокрытые требования. [Проверка механики](docs/assessment_validation.md) отделена от ещё не проведённой калибровки на кандидатах.

Поиск работодателя использует локальный RuBERT-tiny2 с дообучением на конкретных профессиональных задачах. Разметка различает задачи внутри одной специализации. RuBERT выбирает до 50 профилей; локальный mMARCO cross-encoder оценивает профессиональные секции, а калибратор объединяет оба сигнала. Выдача показывает секцию с лучшей итоговой оценкой. При отсутствии строгих совпадений допускаются максимум три приблизительных результата с общей подписью. Зарплата, город, стаж, занятость, язык, портфолио и тестовый балл проверяются SQL; разбор учитывает поддерживаемые отрицания и альтернативы. Тест и ФСП разрешают равенство оценок. Модель не назначает грейд; приблизительный результат не подтверждает пригодность кандидата. [Архитектура, обучение и запуск](docs/semantic_model.md).

Новый контроль всей активной композиции выполнен с заранее зафиксированным авторским эталоном и выявил смысловые ошибки NFC, WebAuthn и виртуальных часов. Прежние функциональные сценарии проходят, качество подбора подтверждено частично. Минимальный профиль без описания задач, проектов или опыта доступен по фильтрам, но может исключаться из смысловой выдачи. Отдельные модули новой политики ранжирования и коротких заданий подготовлены, но ещё не подключены к действующему API/интерфейсу. Подробности и оставшиеся пункты — в [аудите ТЗ](docs/case_status.md).

Профили, анкеты, компания, сохранённые подборки, приглашения, вакансии и отклики находятся в SQLite основного Node.js API: `server/data/assessment.sqlite`. Браузер хранит локальную копию и незавершённые ответы. Версии состояния защищают от незаметного перезаписывания в другой вкладке. Контакты выдаёт отдельный API по действующему согласию и правам участника взаимодействия.

Добавлена регистрация с ролью, именем или названием компании, логином, email и паролем. Аккаунт создаётся после проверки одноразового кода; вход связывает HttpOnly-сессию с постоянным владельцем данных. Для доставки кода на настоящий email необходимо настроить SMTP. Локально без SMTP код сохраняется в игнорируемый `server/data/mail.log`: этот режим проверяет сценарий регистрации, но не подтверждает внешнюю доставку писем. В production без настроенной почты регистрация недоступна. [Что закрыто по ТЗ и что осталось](docs/case_status.md).

В текущем локальном окружении SMTP подключён: сертификат и аутентификация проверены, пользователь получил настоящее письмо и передал код. Код подтвердил аккаунт в отдельной тестовой базе; повторный вход прошёл. Учётные данные находятся только в `.env`; на другом компьютере их нужно настроить отдельно. `test:auth`, `test:access`, `test:contact-privacy`, `test:profile-privacy` и `test:browser` используют собственные временные API, интерфейс и тестовую почту в памяти, без SMTP и рабочей базы.

Проверка доступа: `npm run test:server`, `npm run test:auth`, `npm run test:access`, `npm run test:contact-privacy` и `npm run test:profile-privacy`. Для дополнительного FastAPI установите тестовые зависимости `python -m pip install -r backend/requirements-test.txt` и отдельно выполните `python -m unittest backend.tests.test_access_gate`; тест проверяет временную SQLite и не отправляет письма. Подтверждение почты не проверяет паспортные данные, достоверность опыта, дополнительные контакты анкеты или юридический статус компании.

При подключённом SMTP вводите код из полученного письма. Только в режиме development без SMTP код находится в `server/data/mail.log`: найдите последнюю запись своего email и введите поле `code`. Этот файл не публикуется и не добавляется в Git.

## Запуск

Нужны Node.js 24 или новее и Python 3.11–3.12. Зависимости модели закреплены в `ml/requirements.txt`. Скопируйте `.env.example` в `.env` и заполните почтовые настройки, если нужны настоящие письма.

~~~bash
cp .env.example .env
npm ci --prefix frontend
npm run setup:search
npm run train:search
npm run evaluate:search -- --model server/data/semantic-runs/task-v2
npm run prepare:search-ranker
npm run calibrate:search-score -- --kind qda --output server/data/semantic-runs/task-v2-fused-qda
npm run prepare:search-policy
npm run check:search-model -- --model server/data/semantic-runs/task-v2-search
npm run activate:search-model -- server/data/semantic-runs/task-v2-search
npm run dev
~~~

`npm run dev` запускает Vite на http://127.0.0.1:5173 и Node.js API на http://127.0.0.1:8787; `.env` загружается при запуске API. Для доставки писем укажите `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS`, `SMTP_USER`, `SMTP_PASSWORD` и `SMTP_FROM`. Для SMTP на порту 587 используйте `SMTP_TLS=starttls`; для 465 — `implicit`. Сборка интерфейса: `npm run build`; `npm start` запускает Node.js API и раздаёт готовый сайт на http://127.0.0.1:8787.

Откройте http://127.0.0.1:5173. «Создать аккаунт» открывает регистрацию с выбором роли, а «Войти» возвращает к сохранённому кабинету. У аккаунта роль фиксируется при регистрации. Для проверки приглашений сначала пройдите анкету и тест, включите публикацию своего профиля, затем отправьте ему приглашение из кабинета работодателя. Отдельные браузеры или устройства входят в разные аккаунты и видят общие записи взаимодействия через сервер.

На чистом checkout эти команды обучают энкодер, выполняют локальную диагностику, подготавливают переранжирование и калибровку только по dev, проверяют и активируют композицию. В PowerShell используйте `npm.cmd` вместо `npm`. Первый запуск загружает закреплённые открытые веса; обработка запросов далее локальная. Активная модель выбирается через `server/data/semantic-model/active.json`; последовательность по умолчанию создаёт композицию в `server/data/semantic-runs/task-v2-search`. Веса, локальные снимки, базы и диагностические материалы исключены из Git. При готовой модели пропустите обучение и подготовку, проверьте артефакт и запустите сервис. Повторный запуск не перезаписывает эксперименты. Дообучение по уже просмотренному test запрещено; для следующей настройки нужен независимый контрольный корпус. Сервер готовит модель и индекс в фоне. Отказ модели даёт ошибку сервиса; поиск без текста продолжает работать через фильтры.

### Тестовые аккаунты команды

Для проверки кабинетов без самостоятельной регистрации создайте готовые аккаунты в локальной базе основного Node.js API:

~~~bash
npm run setup:local-accounts
npm run dev
~~~

В PowerShell используйте `npm.cmd`. Откройте [страницу входа](http://127.0.0.1:5173/auth?mode=login).

| Кабинет | Логин | Пароль |
| --- | --- | --- |
| Работодатель | `local_employer` | `LocalDemo2026!` |
| Кандидат | `local_candidate` | `LocalDemo2026!` |

У кандидата подготовлены анкета, учебная категория и история теста. У работодателя — компания, предложение и приглашение кандидату. Результат теста создан служебным скриптом для просмотра интерфейса; это тестовые данные. Вход выполняется через обычную форму, SMTP для подготовки этих аккаунтов не нужен. Повторный запуск сохраняет изменения в уже существующих кабинетах. Для одновременной проверки обеих сторон откройте второй кабинет в инкогнито или другом браузере.

Аккаунты создаются явно командой [scripts/local-accounts.mjs](scripts/local-accounts.mjs) в `server/data/assessment.sqlite`. Сервер распознаёт эту учебную пару по заданным идентификаторам регистрации: обычные пользователи не видят её профили, компании и связи, а учебная пара взаимодействует только между собой. Это действует и для старых записей без признака `synthetic`; изменение полей анкеты не превращает учебный аккаунт в обычный. В интерфейсе происхождение обозначено. Скрипт недоступен в production. После завершения проверки команды эти тестовые аккаунты и команду подготовки можно удалить.

### Дополнительный FastAPI backend

Ветка регистрации также содержит переносимый FastAPI/SQLAlchemy backend для SQLite или PostgreSQL. Он запускается явно через `npm run dev:fastapi` или `npm run start:fastapi` после установки `backend/requirements.txt`; использует отдельную базу `backend/data/hh_platform.sqlite3`. В нём не подключены локальный семантический worker и новые вакансии/отклики основного Node.js API. Гостевой доступ и старые связи с незарегистрированными отправителями закрыты отдельными HTTP-проверками. Полной совместимости с текущим интерфейсом нет: формат состояния FastAPI пока не принимает `candidateDecisions` и не возвращает `contactCandidateIds`. `DATABASE_URL` и контейнер PostgreSQL относятся только к этому варианту. Он не заменяет основной запуск; данные двух backend автоматически не переносятся. Подробнее — в [инструкции FastAPI](docs/fastapi_migration.md) и [описании основного API](server/README.md).

Подробности реализации и границы прототипа — в [описании интерфейса](docs/interface.md).

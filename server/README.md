# Backend платформы

Основной API работает на Node.js 24 со встроенными HTTP, криптографией и SQLite. Банк и ключи ответов загружаются только сервером. Аккаунты, профили, анкеты, компания, сохранённые подборки, приглашения, вакансии и отклики хранятся на сервере; браузер использует локальную копию. Семантический поиск вызывает постоянный локальный Python-worker с дообученным RuBERT-tiny2 и mMARCO cross-encoder; совместную оценку определяет dev-калибровка. Для поиска внешние API и секретные ключи не нужны. Настоящая доставка писем регистрации требует SMTP.

`DirectoryService` применяет `search-ranking.mjs` после смыслового допуска и ограничения ближайших результатов, до пагинации. Тест и ограниченный бонус ФСП помогают выбирать среди близких профилей одной подтверждённой категории; исходные оценки модели сохраняются. Объяснение читает фактический результат этого сравнения и отдельно показывает приоритет подтверждённых анкет. `refresh-tasks.mjs` обслуживает регулярные задания от работодателя ([описание](../docs/employer_tasks.md)). [Актуальный аудит](../docs/case_status.md) описывает проверки и оставшиеся материалы сдачи.

## Запуск

Нужны Node.js 24 или новее и Python 3.11–3.12 для локальной модели. Из корня репозитория при уже подготовленном артефакте:

```bash
cp .env.example .env
npm ci
npm ci --prefix frontend
npm run dev
```

На чистом checkout выполните последовательность из [README](../README.md#запуск): setup, обучение и локальная диагностика энкодера, подготовка reranker, QDA и политики приблизительных результатов, проверка и активация. Нужен Python 3.11–3.12; зависимости закреплены в `ml/requirements.txt`. Первая подготовка загружает открытые веса, далее обработка локальная. Активный артефакт выбирается через `server/data/semantic-model/active.json`; для композиции по умолчанию: `npm run activate:search-model -- server/data/semantic-runs/task-v2-search`. При готовой модели обучение и подготовку пропустите. Активация и worker проверяют файлы, политику, коэффициенты и отпечатки; смена версии переиндексирует каталог. Веса, диагностика и `.venv` исключены из Git. Готовые эксперименты не перезаписываются; дообучение после просмотра test требует нового контрольного корпуса. Пути задаются `SEMANTIC_PYTHON` и `SEMANTIC_MODEL`. [Архитектура и протокол](../docs/semantic_model.md).

`npm run dev` запускает Node.js API на `http://127.0.0.1:8787` и Vite на `http://127.0.0.1:5173`. Vite проксирует `/api`; `.env` загружается при запуске API. После `npm run build` команда `npm start` раздаёт готовый интерфейс и API на порту 8787. В PowerShell используйте `npm.cmd`, если выполнение `npm.ps1` запрещено.

## Хранилище и окружение

Основной API использует `server/data/assessment.sqlite`; путь меняется через `ASSESSMENT_DB`. Отдельные таблицы хранят аккаунты, ожидающие регистрации, сессии, попытки и результаты, профили и профессиональные секции, приглашения, вакансии и отклики. Версия состояния защищает от перезаписи изменений другой вкладкой; устаревший `baseRevision` получает 409. Локальные базы и письма исключены из Git.

| Переменная | Назначение |
| --- | --- |
| `HOST`, `PORT` | Адрес и порт основного API |
| `WEB_ORIGIN` | Разрешённый origin интерфейса |
| `COOKIE_SECURE` | `1` добавляет `Secure` к cookie при HTTPS |
| `ASSESSMENT_DB` | Путь к SQLite основного API |
| `SEMANTIC_PYTHON`, `SEMANTIC_MODEL` | Интерпретатор и артефакт локального worker |
| `NODE_ENV`, `APP_ENV` | Режим среды; production требует настоящую почту |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS` | Адрес, порт и TLS-режим SMTP |
| `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | Учётные данные и отправитель |
| `SMTP_TIMEOUT_MS` | Ограничение ожидания SMTP, по умолчанию 15 секунд |
| `AUTH_CODE_TTL_MINUTES`, `AUTH_SESSION_DAYS` | Срок действия кода и сессии |

Для SMTP на порту 587 используйте `SMTP_TLS=starttls`, на 465 — `implicit`. Без настроенного SMTP в локальной среде код сохраняется в `server/data/mail.log`, а не отправляется на внешний адрес. API сообщает `delivery: 'development'`, но не возвращает код. Этот режим не доказывает доставку email. В production регистрация возвращает ошибку до настройки почты.

В текущем локальном окружении настройки SMTP внесены в игнорируемый `.env`, API перезапущен. Доверенный TLS-сертификат и SMTP-аутентификация проверены; пользователь получил настоящее письмо регистрации и сообщил код. AuthService подтвердил этим кодом аккаунт в отдельной тестовой базе, повторный вход прошёл. Основная база и её аккаунты не изменялись. После изменения `.env` перезапускайте API. Браузерные фикстуры на основном локальном сервисе с SMTP блокируются; проверки с вымышленными получателями запускайте в отдельной среде без реального отправителя.

## Контракт

Полное описание всех маршрутов — запросы, ответы, ошибки, роли и лимиты — в OpenAPI 3.1:

- **Swagger UI:** `http://127.0.0.1:8787/api/docs` (в режиме разработки также `http://localhost:5173/api/docs`);
- **документ:** `GET /api/openapi.json` и файл [docs/api/platform.openapi.json](../docs/api/platform.openapi.json) (`npm run docs:openapi`).

Документ объединяет основной API и [модуль интеграций](../docs/api/integrations.openapi.json). Тест [openapi.test.mjs](tests/openapi.test.mjs) проверяет, что каждый маршрут `server.mjs` описан, все ссылки разрешаются, каждая операция доходит до реального обработчика под нужной ролью, а сохранённый файл совпадает с генератором.

| Группа | Маршруты |
| --- | --- |
| Аккаунт и ФСП ID | `/api/auth/*`, демо-realm `/api/fsp-id/realms/fsp/*` |
| Кабинет | `/api/platform/state` |
| Тестирование | `/api/assessment/program`, `/api/assessment/attempts/{id}` + `/answer`, `/integrity`, `/submit` |
| Подбор | `/api/directory/options`, `/api/directory/search`, `/api/directory/{id}/contacts` |
| Компании и вакансии | `/api/companies`, `/api/vacancies`, `/api/applications` |
| Задания | `/api/tasks`, `/api/tasks/candidates`, `/api/tasks/{id}/answer`, `/review`, `/ai-review` |
| ИИ-помощник | `/api/assistant/info`, `/api/assistant/chat` |
| Модерация банка | `/api/item-bank/*`, `/api/review-bank/variants*` |
| Интеграции и достижения | `/api/integrations/*`, `/api/achievement-claims*`, `/api/moderation/*`, `/api/profile/evidence` |

Ошибки имеют форму `{ "error": "сообщение" }`. Интерфейс отправляет cookie через `credentials: 'same-origin'` и не читает токены из JavaScript.

Контроль теста описан в [assessment_integrity.md](../docs/assessment_integrity.md). Создание и восстановление попытки возвращают `integrity` с `departures`, `blockedCopies` и `lastEventAt`. Клиентское событие не удостоверяет списывание и не влияет на категорию; журнал не доступен работодателю.

`GET /api/platform/state` возвращает текущую идентичность в `X-Platform-Identity`. Для зарегистрированного аккаунта этот заголовок обязателен при `PUT /api/platform/state` и `DELETE /api/auth/account`: отправляйте значение последнего чтения, а при сохранении также `baseRevision`. Если аккаунт изменился, API возвращает конфликт; старый черновик нужно очистить и заново прочитать данные текущего аккаунта. `GET /api/auth/me` без входа возвращает статус отсутствующей авторизации. Удаление состояния без удаления аккаунта запрещено, чтобы сброс не обходил историю анкет и ограничения смены категории.

Без входа доступны регистрация, вход, выход, проверка сессии и `/api/health`. Документы OpenAPI и Swagger UI также публичны. GET-страницы внешнего callback служат только возврату в авторизованный same-origin поток; приём webhook ФСП проверяет подпись и повторы отдельно от браузерной сессии. Эти служебные маршруты не открывают каталог или частные данные. Каталог, компании, состояние кабинета и тестирование требуют подтверждённого аккаунта и действующей сессии; гостю возвращается `401`. `predel_session` используется при обращениях к регистрации и не открывает кабинет или каталог. После входа действует `predel_account_session`. Обе cookie имеют `Path=/api`, `HttpOnly` и `SameSite=Strict`. В базе хранятся хеши случайных токенов, паролей, кодов и сессий. Подтверждённый аккаунт получает новый постоянный кабинет: прежние гостевые данные автоматически не переносятся. Повторный вход с другого устройства связывает новую сессию с тем же аккаунтом. Выход отзывает сессию и очищает cookie. Сохранение частного состояния дополнительно связывается с текущей идентичностью и версией снимка. Подтверждение email доказывает доступ к почтовому ящику, а не личность человека или юридическую подлинность компании.

Код подтверждения действует ограниченное время и блокируется после неверных попыток. Запрос регистрации требует `consent: true` и `privacyVersion`, равную текущей версии из [shared/privacy.ts](../shared/privacy.ts). Версия и время отправки согласия в UTC сохраняются в ожидающей регистрации; после проверки email создаётся событие в `privacy_consent_events`. Старая ожидающая регистрация с другой или отсутствующей версией политики не подтверждается: нужно запросить новый код с текущим согласием. Подтверждённым старым аккаунтам исторические согласия задним числом не добавляются.

Первичное сохранение личной анкеты требует согласия. Изменение согласия на обработку профиля создаёт отдельное событие с версией политики и серверным временем в UTC. Публикация профиля включается отдельно. Обычный PUT не может изменить или убрать ранее сохранённую анкету; новая анкета использует новый ID. Результат и категория подтверждаются серверной попыткой. Правильные ответы не выдаются через API, а попытка дополнительно защищена токеном. Контакты раскрываются своему работодателю после принятия приглашения или самостоятельного отклика и только при действующем согласии кандидата.

Аккаунты, состояние кабинета, тесты и интеграции основного Node.js API используют общее соединение SQLite. Удаление аккаунта в общей транзакции очищает его профиль, анкеты, попытки и события контроля, компании/вакансии/отклики, подборки, приглашения, согласия, подключения источников, credentials и частные заявки модерации. Все серверные сессии становятся недействительными. При сбое удаления транзакция откатывает связанные изменения; поздний ответ источника не восстанавливает удалённый профиль. Остаются только случайный номер операции и время удаления без ссылки на аккаунт; общий каталог официальных публикаций и технические идентификаторы webhook не являются записями частного кабинета. Удаление не очищает чужие браузеры и резервные копии автоматически.

Регистрация, вход, согласия, неизменность анкет и удаление проверены на изолированных данных; [серверный сценарий](tests/registration-privacy.test.mjs), [браузерный сценарий](../frontend/tests/registration-privacy.mjs) и [статус ТЗ](../docs/case_status.md). Дополнительный FastAPI хранит данные отдельно и не синхронизируется с Node.js.

## Внешние подтверждения

Основной Node.js backend поддерживает подключения внешних источников, фоновую синхронизацию достижений, зашифрованные токены и подписанный webhook. В профиле кандидата появился раздел «Внешние подтверждения». Сессионный `fsp-demo` обслуживает отдельный строгий сервис: учебный источник обозначен как демо, его ограниченное влияние на порядок не считается реальным подтверждением. Общий реестр провайдеров этот маршрут не подменяет. `fsp` включается после настройки OIDC и согласованного ресурсного API. Это не заявленная работающая интеграция с настоящим реестром: его официальный контракт и доступ ещё нужно получить.

[Контракты, конфигурация и жизненный цикл](../docs/integrations.md), [OpenAPI наших маршрутов](../docs/api/integrations.openapi.json), [предложение контракта ФСП](../docs/api/fsp-provider.openapi.json). Спецификация модуля доступна на `/api/integrations/openapi.json`; она не заменяет полное описание остальных маршрутов Node.js API.

## Каталог и данные тестов

Потребности работодателя сохраняются через `state.hiringNeeds` в отдельной таблице `platform_hiring_needs` с ключом `(owner,id)`, индексом порядка и каскадным удалением. До 20 записей с названием, командой, задачами и проверенными фильтрами. Запись требует роли работодателя, актуальных идентичности и ревизии; старый PUT без поля сохраняет коллекцию. Потребность не публикуется как вакансия. [Контракт и проверки](../docs/employer_needs.md).

Смысловая выдача возвращает `categories` по всем допущенным кандидатам до пагинации: подтверждённые специализация/грейд, `count`, `demoCount`, до трёх публичных `candidateIds`, `reason` и `approximate`. Учебные профили входят в общий счётчик; их число названо в причине. Версия — `model.categoryRecommendationPolicy`. Дополнительный JSON-параметр `category` с `{specialization,grade}` сужает только кандидатов и их `total`, оставляя рекомендации и исходные фильтры; в ответе есть `selectedCategory`. Неверный JSON/словарь возвращает `400`. Права и согласие проверяются до группировки, контактов в агрегате нет.

Зарегистрированный обычный работодатель видит опубликованных обычных кандидатов и встроенный вымышленный демокаталог даже на чистой базе. [Правило происхождения](demo-catalog.mjs) допускает только встроенный ID, отсутствие владельца и серверный признак синтетической записи. [Публичный DTO](directory-store.mjs) вычисляет `demoProfile: true` и возвращает пустые контакты; присланное или сохранённое клиентом поле не даёт права на показ. Произвольные записи без владельца и прежние гостевые профили остаются скрытыми. Эта область доступа применяется к поиску, вариантам фильтров и повторной проверке после worker.

Демопрофили доступны для чтения; работодатель может сохранить свои решения «нравится»/«пропустить» и вернуть избранное при новом входе. Они не являются участниками взаимодействия: API запрещает приглашения и контакты, а `contactCandidateIds` не включает их даже при некорректных старых связях. В интерфейсе показана метка «Демо», кнопки приглашения отсутствуют. Реальные приглашения и раскрытие контактов продолжают проверять зарегистрированных участников, владельца и действующее согласие. Локальная учебная пара находится в отдельной области и взаимодействует только между собой; обычные пользователи не видят её, а `local_employer` не получает общий демокаталог. Гостю рабочие маршруты возвращают `401`; роль кандидата получает `403` при обращении к поиску и вариантам фильтров.

[HTTP-регрессия](tests/demo-catalog-access.test.mjs) проверяет чистую базу, полный проход страниц, фильтры, происхождение, сохранение решений между сессиями, недоверенные старые связи и изменение доступа во время обработки запроса. [Браузерная проверка](../frontend/tests/demo-catalog.mjs) проходит обычную регистрацию, список и карточки, фильтры, просмотр, PDF, избранное и изоляцию локальной пары. Для этих проверок почта остаётся в памяти, база отдельная, worker детерминированный: это подтверждение механики, а не оценка ML-релевантности. Автономные проверки модели через `DirectoryService` без `accountForOwner` не доказывали доступность каталога через авторизованный HTTP API. Массовый импорт внешних профилей не реализован; отсутствие предоставленного способа загрузки закрытого набора жюри отмечено в [аудите](../docs/case_status.md).

Дополнительно прошёл авторизованный HTTP-запрос в отдельном сервисе с настоящим `SemanticWorker` и локальными весами: новый обычный работодатель получил демопрофили по профессиональному тексту с `demoProfile` и пустыми контактами. Регистрация использовала почту в памяти, рабочая SQLite не открывалась. Этот проход подтверждает доступность реального модельного пути; независимой проверки релевантности он не заменяет.

Концепция будущего ATS API описана отдельно в [ats_integration.md](../docs/ats_integration.md), [предлагаемом OpenAPI](../docs/contracts/ats.openapi.json) и [примерах обмена](../docs/examples/ats/README.md). Маршруты `/api/ats/v1`, интеграционные токены, inbox/outbox и внешние сопоставления сейчас не реализованы. Этот проект контракта не заменяет описание действующих маршрутов выше и не означает готового подключения к ATS.

Тексты очищаются от email и телефонов. Секции до 4000 символов и 12 000 символов на профиль кодируются окнами по 256 токенов с перекрытием 64; CLS-векторы окон нормируются, усредняются и снова нормируются. RuBERT выбирает до 50 профилей. Второй этап оценивает фактические рабочие секции, объединяя их собственный косинус с cross-encoder logit. Максимальная совместная оценка задаёт смысловой допуск и объяснение. Затем `search-ranking.mjs` переставляет близкие результаты одной подтверждённой категории по тесту и ограниченному фактору ФСП, сохраняя исходные оценки и позиции других категорий; пагинация выполняется после этого. Применённое правило возвращается в `model.categoryRankingPolicy`. Фактор ФСП использует доверенные активные записи ФСП или одобренную принадлежность официального результата; учебный источник остаётся отдельно помеченным демо. Ручной ID, клиентский флаг и стороннее портфолио этого фактора не дают. SQL проверяет зарплату, город, стаж, занятость, язык, категорию, портфолио и балл; `interpreted` и `effectiveFilters` показывают применённые условия. Если строгих результатов нет, dev-политика допускает до трёх ближайших выше отдельного порога: `approximate: true` и одно сообщение в `warnings`. Их состав и лимит определяются до учёта силы профиля. Ошибки модели дают 503. После ожидания моделей повторно проверяются согласие, публикация, текст и версия; смена модели не позволяет записать старые векторы под новой версией. Фильтры без текста работают отдельно. Сервер готовит модель и индекс в фоне; первый запрос ждёт подготовки.

Банк тестов находится в `server/banks`, исходный каталог — в `server/directory-seed.mjs`. Основной Node.js API использует эти источники напрямую. Ограничители запросов находятся в памяти одного процесса; для нескольких экземпляров сервиса потребуется общее хранилище.

## Дополнительный FastAPI backend

`npm run dev:fastapi` и `npm run start:fastapi` запускают отдельный FastAPI/SQLAlchemy вариант после установки `backend/requirements.txt`. Его база — `backend/data/hh_platform.sqlite3` либо `DATABASE_URL`; PostgreSQL Compose относится к этому варианту. Он имеет собственный OpenAPI на `/openapi.json`, но не содержит локальный semantic worker и новые marketplace-эндпоинты. Доступность встроенного демокаталога и поле `demoProfile` добавлены только в основной Node.js API; FastAPI по-прежнему исключает учебные записи. Данные и поведение основного API автоматически не переносятся. Полная инструкция и ограничения — в [docs/fastapi_migration.md](../docs/fastapi_migration.md).

## Внешние подтверждения основного Node.js API

Эти модули работают в основном сервере и не перенесены в дополнительный FastAPI. [OpenAPI интеграций](../docs/api/integrations.openapi.json) описывает маршруты внешних подтверждений; полного контракта остальных основных API этот файл не заменяет.

Пилот без API ФСП: `GET /api/integrations/fsp-public/search?name=Фамилия%20Имя`, сессия кандидата и согласие профиля. 24 проверенные записи одного официального протокола, все `unverified`. Запуск OCR: `npm run import:fsp-public`; подробности в [исследовании](../docs/fsp-public-research.md).

Заявки: `/api/achievement-claims`; очередь и решения: `/api/moderation/claims`; хеш официального источника: `/api/moderation/sources/{sourceId}/check`. Доступ к модерации назначается только серверной командой `npm run moderator -- grant <login-or-email>`, отзывается `revoke`. [Документация](../docs/achievement-moderation.md).

[Парсинг результатов из официальных таблиц и новостей](../docs/public-achievements.md): реестр источников, очередь обновлений, поиск команды/участника и подтверждение через модерацию.

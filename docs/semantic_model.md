# Семантическая модель подбора

Подбор сопоставляет описание потребности работодателя с профессиональными задачами кандидата. Локальный RuBERT-tiny2 кодирует запрос и секции профиля, а mMARCO MiniLMv2 cross-encoder совместно рассматривает запрос и профессиональный текст. Калибратор объединяет эти сигналы для порядка выдачи и отсечения неподходящих пар. Зарплата и другие обязательные ограничения проверяются отдельно в SQLite.

Модель не назначает грейд и не подтверждает квалификацию. Основание подтверждённой категории — успешная серверная попытка теста. Фрагмент профиля в выдаче позволяет проверить, какие сведения участвовали в подборе; он не объясняет внутренние признаки нейросети.

## Открытые модели

Энкодер — [cointegrated/rubert-tiny2](https://huggingface.co/cointegrated/rubert-tiny2/blob/e8ed3b0c8bbf4fb6984c3de043bf7d2f4e5969ae/README.md), лицензия MIT. Исходная ревизия закреплена: `e8ed3b0c8bbf4fb6984c3de043bf7d2f4e5969ae`. Проект дообучает весь `AutoModel`, включая embeddings и transformer-слои, а не только внешнюю проекцию. В энкодере 29 193 768 обучаемых параметров; размерность нормированного CLS-вектора — 312.

Второй этап — [cross-encoder/mmarco-mMiniLMv2-L12-H384-v1](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1), лицензия Apache-2.0, ревизия `1427fd652930e4ba29e8149678df786c240d8825`. Это опубликованная модель совместной оценки запроса и документа. Её веса в проекте не дообучаются: собственное обучение относится к RuBERT, а настройка сочетания сигналов выполняется на dev-части корпуса.

Используются локальные Safetensors и tokenizer с `trust_remote_code=False`. Первая подготовка загружает закреплённые открытые веса и проверяет файлы по манифесту. Готовый worker не скачивает модель и не отправляет запрос пользователя во внешние сервисы. Веса и данные локальных запусков исключены из Git.

## Как выполняется поиск

1. Сервер проверяет публикацию профиля, согласие и подтверждённую категорию. SQL применяет специализацию, грейд, стек, город, зарплату, стаж, формат и занятость, язык, портфолио, тестовый балл и достижения ФСП.
2. Из свободного запроса выделяются поддерживаемые явные ограничения: например, рублёвый бюджет, грейд или отрицание направления. Они применяются отдельно; описание задачи передаётся модели. Для ограниченного списка явно названных профессиональных методов сервер дополнительно проверяет положительные сведения профиля. Правила разбора не гарантируют понимания любой формулировки, а близость векторов не проверяет зарплату.
3. Постоянный Python-worker кодирует описание задачи. Сервер сравнивает его с профессиональными секциями подходящих профилей и выбирает короткий список до 50 кандидатов. Для запроса только с распознанными ограничениями используется выдача по фильтрам без вызова моделей.
4. Cross-encoder получает запрос и фактические секции профиля с каноническим названием специализации. Калибратор объединяет косинус и logit одной и той же секции. Максимальная совместная оценка определяет порядок профиля; при равенстве учитываются исходный косинус, тест и ФСП.
5. В выдаче показаны сведения о категории и секция с максимальной итоговой оценкой. Если строгих совпадений нет, отдельная политика допускает максимум три ближайших профиля с победившей профессиональной секцией выше порога применимости запроса. Роль и стек минимального профиля допускаются только выше строгого порога. Приблизительные результаты помечены `approximate: true`, а интерфейс показывает предупреждение. При наличии строгих результатов приблизительные не добавляются.

Если модель отсутствует или отказал этап оценки, текстовый подбор возвращает ошибку сервиса. Поиск без текста продолжает работать через структурированные фильтры. После ожидания моделей сервер повторно проверяет публикацию, согласие, профессиональный текст и версию индекса: изменившийся профиль исключается, смена модели приводит к ошибке сервиса.

### Явно названные профессиональные методы

`server/search-evidence.mjs` содержит ограниченный список методов и их явных синонимов: например, NFC, BLE/GATT, WebAuthn/FIDO2, аппаратные аутентификаторы, OAuth, OIDC и gRPC. Эта проверка различает близкие задачи: экран штрихкода не подтверждает чтение NFC, а пароль или одноразовый код не подтверждают работу с аппаратным ключом. Общее описание задачи без распознанного метода продолжает оцениваться моделью. Не каждый термин запроса превращается в обязательный фильтр, правила не охватывают все технологии и способы выражения опыта.

Требования извлекаются из профессиональных частей запроса: сохраняются вводный запрос о найме без заголовка, явно выделенная задача и профессиональные требования; описание компании и условий отделяется. «NFC или BLE» требует одного из вариантов, «NFC и BLE» — обоих; желательные и исключённые методы не становятся обязательными. Положительное фактическое утверждение может подтвердить более позднюю работу после старого отрицания опыта. Заявленная роль или стек дополняют отсутствующие сведения только у профиля без исходных `bio` и `workHistory` и не перекрывают явное отрицание того же метода в образовании или достижениях.

Проверка читает полные исходные профессиональные поля в пределах их валидации, очищенные от контактов и служебных подписей синтетических данных. Ограничение модельной секции в 4000 символов к этой локальной проверке не применяется: оно могло бы оборвать отрицание или скрыть последующее положительное утверждение. Ограничения учитываются в свежем снимке до короткого списка и после ожидания модели, для строгой и приблизительной выдачи, включая старый режим только с косинусом. Поиск без текста сохраняет точные SQL-фильтры. Баллы теста, записи ФСП и софт-скиллы не служат свидетельством конкретного метода.

### Профессии вне каталога

Платформа подбирает ИТ-специалистов. Локальный справочник `server/data-definitions/professional-role-scope.json` содержит однозначные профессии вне каталога: канонические названия и ID взяты из [открытого справочника hh.ru](https://api.hh.ru/professional_roles), склонения и бытовые синонимы заданы локальными правилами. Запрос пользователя во внешний сервис не отправляется.

`query-role-scope.mjs` проверяет явно запрошенную профессию после «нужен», «ищем», «требуется» и подобных конструкций. Запрос бухгалтера для составления деклараций получает пустой результат до запуска модели; запрос разработки бухгалтерской системы продолжает семантический поиск. Отрицания и альтернативы с ИТ-профессией учитываются. Неоднозначные названия вроде инженера, аналитика или дизайнера остаются запросами модели. API сообщает распознанную внешнюю профессию в `interpreted.unsupportedRole`. Правила не покрывают любые новые названия и описания без явной профессии.

## Секции профиля и индекс

`semanticSegments` в `server/directory-store.mjs` готовит тексты из `bio`, `workHistory`, `careerAchievements`, `education` и роли со стеком. Перед ограничением длины из модельного текста удаляются распознанные явные отрицания собственного опыта и планы будущего обучения; исходные публичные поля сохраняются. Технические утверждения вроде «не допускаю повторов» остаются положительными сведениями. Точные повторы удаляются. На секцию приходится до 4000 символов, на профиль — до 12 000 символов и восьми секций. Пустые поля не заменяются придуманными описаниями.

Имена, контакты, зарплата и тестовый балл не входят в эмбеддинг; email и телефоны дополнительно удаляются из свободных полей. Личные резюме из проверки импорта не используются для обучения. У известных синтетических профилей из секций удаляются служебные подписи фабрики данных; публичная пометка о вымышленном происхождении остаётся видимой. Это правило не удаляет похожие фразы из профессиональных сведений реальных профилей.

Каждая секция кодируется независимо. SQLite хранит JSON-массив секций и его хеш, а BLOB — нормированные Float32-векторы. Первый этап использует максимальное сходство секции с запросом. Во втором этапе рассматриваются положительные секции `bio`, `workHistory`, `careerAchievements` и `education`. Если исходные `bio` и `workHistory` отсутствуют, дополнительно оценивается фактическая роль со стеком; образование и достижения не блокируют эту секцию. Наличие исходного описания, включая отрицание опыта, сохраняет оценку описанных профессиональных сведений без замены их стеком. Победившие роль и навыки обозначаются в API как `evidenceKind: "competencies"` и объясняются фразой «Роль и навыки в профиле»; это заявленные компетенции, а не описание выполненной работы.

Политика `task-v2` обрабатывает длинные тексты окнами до 256 токенов с перекрытием 64 токена. CLS-векторы окон нормируются, усредняются и снова нормируются. Усреднение может ослабить короткую важную задачу внутри длинной секции. Cross-encoder ограничивает пару 512 токенами с обрезкой `longest-first`; часть длинного текста может не попасть во второй этап.

SHA-256 весов и политика кодирования образуют `encodingFingerprint`. Версия индекса дополнительно включает `positive-profile-sections-max-v3`; API сообщает её в `model.indexPolicy`. Старые векторы пересчитываются при следующем индексировании, а открытие SQLite обновляет документы из сохранённых публичных полей. Изменение модели, политики секций или профессионального текста также вызывает переиндексацию. У старых артефактов сохраняется их собственная политика кодирования.

API отдельно сообщает `model.profileEvidencePolicy: "professional-sections-with-strict-sparse-competencies-v2"` и `model.taskEvidencePolicy: "explicit-professional-concepts-v1"`. Это правила подготовки и допуска сведений сервера. Веса модели, формула объединения косинуса и logit одной секции, пороги строгой и приблизительной выдачи и закреплённый дескриптор калибровки не меняются. Порог приблизительного допуска настроен на описания профессиональных задач, поэтому не применяется к победившей секции роли и навыков даже при явно указанной профессии или фильтре специализации. Такая секция проходит только строгий порог. Метрики dev-калибровки профессиональных задач не подтверждают качество новой секции заявленных компетенций; для него нужна отдельная проверка с реальной моделью.

## Корпус и обучение

`ml/dataset_v2.py` содержит авторский синтетический корпус профессиональных задач для 14 направлений каталога. Персональных данных, реальных резюме и результатов найма в нём нет. Разметка различает задачи внутри одной профессии: принадлежность одной специализации сама по себе не делает описания релевантными друг другу.

Запрос содержит `relevant` — ID конкретных подходящих описаний. Посторонний запрос имеет пустой список релевантных документов. Единица разделения train/dev/test — целое семейство задачи: связанные описания и формулировки запроса не распределяются по разным частям. Проверяются уникальность ID и нормализованных текстов. Все профессии каталога встречаются в train; отложенные части содержат новые семейства задач знакомых профессий.

`ml/train.py` обучает энкодер только на train-запросах и train-описаниях. Для положительной пары выбираются нерелевантные задачи той же профессии, другие профессии и посторонние train-тексты. Сложные отрицательные примеры обновляются по текущему энкодеру; dev и test в этом выборе не участвуют. Используется контрастивная функция потерь и AdamW; фактические аргументы запуска, среда и хеши записываются в метаданные.

Checkpoint, пороги и сочетание сигналов выбираются по dev. Test не используется для обучения или настройки. Для совместной оценки реализованы LDA и QDA с двумя признаками одной пары: косинус RuBERT и сырой logit cross-encoder. При калибровке нейросетевые веса не меняются. Порог строгих пар и порог применимости запроса хранятся отдельно: приблизительные результаты не объявляются строгими совпадениями.

Разметка создана командой и не подтверждена независимыми экспертами. Синтетический корпус и функциональные сценарии позволяют проверить реализацию, но не подтверждают пригодность конкретного человека для найма. Независимая проверка на реальных потребностях и резюме остаётся отдельной работой. Подходящий кандидат вне короткого списка не дойдёт до второго этапа; при нескольких секциях и приблизительной выдаче возможно случайное совпадение.

## Артефакты

Каждый запуск обучения создаёт отдельную папку в `server/data/semantic-runs/`: веса, tokenizer, снимок `dataset.json`, копии исходного кода с хешами, параметры и состояние запуска. Локальные диагностические результаты сохраняются рядом с артефактом и не входят в продуктовый отчёт.

`train.py` отказывается перезаписывать существующий запуск. Реестр `server/data/semantic-evaluations/` фиксирует просмотр holdout по его содержимому: переименование папки не разрешает дообучение на уже просмотренном test. Для настройки после изучения его ошибок нужен новый независимый контрольный набор. Повторная проверка неизменного артефакта читает сохранённые результаты.

Активная модель выбирается через `server/data/semantic-model/active.json`. Активация проверяет метаданные, SHA-256 весов, файлы второго этапа и отпечаток композиции до атомарной замены указателя. Worker повторяет проверки при загрузке. Источник истины об активной версии — этот указатель и `metadata.json` выбранного артефакта. Проверки команд не запрещают ручное изменение файлов операционной системой.

Веса, tokenizer, HF cache, снимки запусков, базы, диагностические файлы и `.venv` исключены из Git. Детерминированные операции и фиксированный seed помогают воспроизвести процедуру, но не гарантируют побитовую идентичность весов между версиями PyTorch и оборудованием.

## Локальная подготовка и запуск

Нужны Node.js 24 или новее и Python 3.11–3.12. Зависимости закреплены в `ml/requirements.txt`; обёртка `scripts/ml.mjs` использует `.venv`. На чистом checkout последовательность для композиции по умолчанию:

```powershell
npm ci --prefix frontend
npm run setup:search
npm run train:search
npm run evaluate:search -- --model server/data/semantic-runs/task-v2
npm run prepare:search-ranker
npm run calibrate:search-score -- --kind qda --output server/data/semantic-runs/task-v2-fused-qda
npm run prepare:search-policy
npm run check:search-model -- --model server/data/semantic-runs/task-v2-search
npm run activate:search-model -- server/data/semantic-runs/task-v2-search
npm run dev
```

Откройте http://127.0.0.1:5173. При готовой композиции обучение и подготовку пропустите: достаточно проверить артефакт, активировать его и запустить сервис. Обучение по умолчанию активирует энкодер; последний `activate:search-model` переключает приложение на готовую композицию со вторым этапом. Результаты диагностики остаются в игнорируемой `server/data/`.

В PowerShell при ограничении запуска скриптов используйте `npm.cmd` вместо `npm`. На Windows интерпретатор — `.venv/Scripts/python.exe`, на Linux — `.venv/bin/python`. Пути можно задать через `SEMANTIC_PYTHON` и `SEMANTIC_MODEL`. Сборка: `npm run build`; запуск собранного сайта и API: `npm start`, адрес http://127.0.0.1:8787.

Функциональная проверка активной модели без изменения базы приложения:

```powershell
npm run check:search-model
npm run test:search-quality
```

Она проверяет известные сценарии и не разрешает подбирать веса по уже просмотренному test. Исправления сервера сопровождаются повторной регрессией затронутого поведения.

## Протокол worker

Для диагностики:

```powershell
.venv\Scripts\python -X utf8 ml/worker.py --model server/data/semantic-runs/task-v2-search --threads 4
```

Ввод и вывод — UTF-8 JSONL. Запрос `{ "id": "q1", "texts": ["описание потребности"] }` получает `{ "id": "q1", "vectors": [[...312 чисел...]] }`. Health-запрос `{ "id": "h", "kind": "health" }` сообщает версию и политику модели. Запрос `{ "id": "r1", "kind": "rerank", "query": "описание потребности", "texts": ["роль\nописание задачи"] }` возвращает `scores` с исходными логитами.

Допускается до 256 текстов по 12 000 символов; запрос переранжирования ограничен 1200 символами. Стандартный вывод содержит только протокол, профессиональные тексты не логируются. В API `semanticScore` — исходный косинус отбора, `rerankerScore` — logit итоговой секции, `rank` — совместная оценка. Эти значения не являются вероятностью найма или уверенностью в грейде.

# Семантическая модель подбора

Подбор сопоставляет описание потребности работодателя с профессиональными задачами кандидата. Дообученный локальный **RuBERT-tiny2** кодирует запрос и отдельные профессиональные секции профиля в нормированные векторы из 312 чисел. Максимальное косинусное сходство выбирает короткий список кандидатов. Затем локальный **mMARCO MiniLMv2 cross-encoder** оценивает пары «запрос — фактическая секция» совместно. Калибратор объединяет оба сигнала для порядка и отсечения. Оценки не являются вероятностью найма, доказательством компетенции или подтверждением грейда.

В версии **task-v2** обучение и оценка различают конкретные задачи внутри одной профессии. Например, два специалиста Embedded могут работать с энергопотреблением автономного устройства и с управлением двигателем: общая специализация сама по себе не делает оба профиля релевантными любой из этих потребностей. Проверяемая релевантность задаётся явными связями запроса с описаниями задач, а не совпадением названия профессии.

## Модель и требования

ТЗ, §2.1–2.2, требует подбора по подтверждённым тестированием категориям, объяснения выдачи и фильтров специализации, грейда, категории, стека и подтверждённых достижений ФСП. ML/NLP назван преимуществом. Модель не назначает грейд и не заменяет серверный тест.

Исходная [RuBERT-tiny2](https://huggingface.co/cointegrated/rubert-tiny2/blob/e8ed3b0c8bbf4fb6984c3de043bf7d2f4e5969ae/README.md) опубликована под MIT, ориентирована на русский язык и допускает дообучение для прикладной задачи. Авторский пример использует CLS-вектор с L2-нормированием и размерностью 312. Исходная ревизия закреплена: `e8ed3b0c8bbf4fb6984c3de043bf7d2f4e5969ae`.

Проект обучает весь `AutoModel`: embeddings и transformer-слои, а не только внешнюю проекцию. В энкодере 29 193 768 обучаемых параметров. Используются Safetensors, `trust_remote_code=False` и локальная CPU-среда. Первый запуск подготовки модели требует интернета; готовый worker не скачивает веса при запросе пользователя.

## Как выполняется поиск

1. Сервер проверяет публикацию профиля, согласие и подтверждённую категорию. Структурированные ограничения применяются к данным SQLite: специализация, грейд, стек, город, зарплата, стаж, формат и занятость, язык, портфолио, тестовый балл и достижения ФСП.
2. Из свободного текста выделяются поддерживаемые явные ограничения: например, рублёвый бюджет, указанный грейд или отрицание направления. Распознанные ограничения применяются отдельно, а оставшееся описание задачи передаётся модели. Это отдельные правила разбора запроса; косинусное сходство не проверяет зарплату и не гарантирует понимания любой формулировки отрицания.
3. Профессиональные секции включают описание задач, историю работы, достижения, образование и роль со стеком. Отдельные поля имени, контактов, зарплаты и тестового балла не входят в эмбеддинг; адреса и телефоны дополнительно удаляются из свободных полей. Персональные резюме из проверки импорта не используются для обучения модели.
4. Постоянный Python-worker кодирует описание задачи. Сервер сравнивает его с векторами секций подходящих профилей и выбирает до **50 кандидатов** по максимальному сходству. Перед вторым этапом порог косинуса не применяется. Cross-encoder получает запрос и все фактические профессиональные секции с каноническим названием специализации; роль со стеком используется только в первом этапе. Пакеты ограничены 256 парами. Калибратор оценивает косинус и logit **одной и той же секции**, после чего выбирается максимальная совместная оценка профиля. При равенстве учитываются исходный косинус, тест и ФСП. Для запроса только с распознанными ограничениями используется выдача по фильтрам без вызова моделей.
5. Выдача содержит фрагмент секции с максимальной итоговой оценкой и сведения о категории. Фрагмент помогает проверить совпадение задач, но не является объяснением внутренних признаков нейросети. Если строгих совпадений нет, отдельная политика допускает максимум три ближайших профиля выше dev-порога применимости запроса. Они помечены `approximate: true`; интерфейс показывает одно предупреждение о приблизительных совпадениях. Наличие строгих результатов исключает добавление слабых.

Если модель отсутствует или остановилась, текстовый подбор возвращает ошибку сервиса. Поиск без текста продолжает работать через структурированные фильтры.

### Второй этап оценки

Используется [cross-encoder/mmarco-mMiniLMv2-L12-H384-v1](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1), Apache-2.0, закреплённая ревизия `1427fd652930e4ba29e8149678df786c240d8825`. Это опубликованная модель совместной оценки запроса и документа, обученная на многоязычном mMARCO. **Её веса в проекте не дообучались.** Собственное дообучение относится к RuBERT. Для cross-encoder только определён порог на исходной dev-части task-v2: 50 запросов × 140 документов, всего 7000 пар, F1 отдельных размеченных пар с разрешением равенства по precision и recall. Test и функциональные 42 сценария не выбирают этот порог.

Ввод второго этапа одинаков в калибровке и поиске: каноническое название специализации, новая строка, профессиональное описание задачи. В приложении этим описанием становится каждая непустая секция `bio`, `workHistory`, `careerAchievements` или `education`. Для быстрого первого поиска допускается удаление нейтрального начала «Нужен человек…». В совместной оценке это начало сохраняется, как в калибровке; выделение задачи по заголовку и удаление распознанных SQL-ограничений остаются общими. Максимум — **512 токенов на пару**, обрезка `longest-first`, динамическое дополнение до длины пакета. Выход cross-encoder — один **сырой logit**, без преобразования в вероятность. В API `semanticScore` сохраняет исходный косинус отбора, `rerankerScore` — logit итоговой секции, `rank` — совместную оценку; последние два значения могут выходить за `[-1, 1]`.

Для объединения сигналов реализованы LDA и QDA с фиксированным уменьшением ковариаций к диагонали на **10%**, равными априорными весами классов и двумя признаками: косинус RuBERT для сырого профессионального запроса и секции без роли; logit cross-encoder для того же запроса и секции с ролью. LDA использует линейную комбинацию, QDA добавляет квадратичную форму. Общее максимальное сходство профиля не подставляется вместо косинуса конкретной пары. Коэффициенты и порог определены только на 7000 dev-парах; нейросетевые веса при калибровке не меняются.

На использованном dev LDA дал pair F1 **0,697368** и nDCG@5 **0,903524**, QDA — **0,716216** и **0,934599**. Это **resubstitution**: коэффициенты и порог получены на том же dev, на котором рассчитаны эти числа. Они помогают выбрать калибровку, но не являются независимой оценкой качества. Порог строгих пар QDA — **6,0718039587067905**; параметры и SHA сохраняются в отдельном артефакте. Исходные артефакты остаются неизменными.

Отдельный порог применимости запроса выбран по максимуму dev-оценки на запрос и F1 наличия релевантных документов. У QDA он равен **0,86792455** (полное значение в метаданных). На использованном dev политика устраняет восемь пустых выдач для положительных запросов, но принимает **два из восьми посторонних запросов**. Поэтому этот порог не заменяет строгий порог всех пар: ближайшие профили допускаются только при отсутствии строгих результатов и ограничиваются тремя. Эти dev-числа также являются калибровочными, а не доказательством надёжного распознавания любой посторонней профессии.

Готовый worker использует только локальные Safetensors и tokenizer с `trust_remote_code=False`. Подготовка загружает семь файлов закреплённой ревизии, проверяет их опубликованные SHA-256 и сохраняет манифест. Каждый запуск worker повторно проверяет файлы, политику, порог и версию. Версия всей композиции включает отпечаток RuBERT и версии второго этапа. Исходный task-v2 не перезаписывается: композиция хранится отдельным артефактом.

После ожидания второго этапа сервер повторно проверяет публикацию, согласие, содержимое профиля и версию индекса. Изменившийся профиль исключается; смена модели приводит к 503. Для артефакта с объявленным cross-encoder отказ второго этапа также даёт 503. Отдельный старый артефакт без второго этапа сохраняет поиск по косинусу и собственному исходному порогу.

Ограничения: подходящий кандидат вне первых 50 не дойдёт до второго этапа; часть длинной секции может отсечься после 512 токенов. Dev-порог для коротких описаний не подтверждён независимыми реальными полными профилями. Максимум нескольких секций и режим приблизительных результатов повышают вероятность случайного совпадения. Уже просмотренный test энкодера не объявляется новой независимой проверкой всей композиции.

### Профессии вне каталога

Платформа подбирает ИТ-специалистов. Локальный справочник `server/data-definitions/professional-role-scope.json` содержит 80 однозначных профессий вне этого каталога: канонические названия и ID взяты из [открытого справочника hh.ru](https://api.hh.ru/professional_roles), склонения и бытовые синонимы заданы локальными правилами. Запрос пользователя во внешний сервис не отправляется.

`query-role-scope.mjs` проверяет только явно запрошенную профессию после «нужен», «ищем», «требуется» и подобных конструкций. Например, запрос бухгалтера для составления деклараций получает пустой результат до запуска модели. Запрос разработки бухгалтерской системы продолжает семантический поиск. Отрицания и допустимые альтернативы с ИТ-профессией учитываются; неоднозначные названия вроде инженера, аналитика или дизайнера остаются запросами модели. API сообщает распознанные внешние профессии в `interpreted.unsupportedRole`. Правила не гарантируют определение любых новых названий или описаний без явной профессии.

## Секции профиля и индекс

`semanticSegments` в `server/directory-store.mjs` готовит отдельные тексты: `bio`, `workHistory`, `careerAchievements`, `education` и роль со стеком. Точные повторы удаляются. На секцию приходится до 4000 символов, на профиль — до 12 000 символов и восьми секций. Пустые поля не заменяются придуманными описаниями. У профиля без профессионального текста остаётся поиск по точным фильтрам, но нет семантического совпадения.

Для известных синтетических демонстрационных профилей строки фабрики «Демонстрационный профиль:», «Демонстрационные данные:» и «Результат демонстрационного проекта:» обозначают происхождение данных. Они исключаются из профессиональных секций, а соответствующий metadata suffix истории работы после новой строки удаляется. Это правило применяется только при `synthetic === true`: реальные образование и достижения сохраняются, в том числе если содержат похожие фразы. Публичные подписи о вымышленном происхождении данных остаются видимыми.

Каждая секция проходит обычный энкодер независимо. В SQLite поле `document` содержит JSON-массив секций, а его хеш учитывает состав и порядок этих текстов. BLOB хранит подряд несколько Float32-векторов; для `n` секций это `312 × n` чисел. Первый поиск использует максимальное скалярное произведение запроса с секцией. Без второго этапа она становится текстовым основанием совпадения; с ним основание выбирается по максимальной совместной оценке фактических профессиональных секций. Исходный порог энкодера сохраняется в метаданных; при наличии второго этапа он не отсекает короткий список.

Версия индекса — версия модели плюс `profile-sections-max-v2`; API сообщает её отдельно в `model.indexPolicy`. Замена весов, политики секций или профессионального текста приводит к переиндексации. Старые объединённые документы восстанавливаются из публичных профессиональных полей при открытии SQLite. Одновременно пересанитизируются старые публичные поля имени, роли и стека; владелец, подтверждённость и приватные записи аккаунта не изменяются этой миграцией.

Максимум нескольких оценок позволяет короткой подходящей задаче сохраниться среди общих сведений, но также повышает шанс случайного совпадения. Рабочий порог получен на dev-парах «один запрос — одно описание задачи», а не на максимуме секций полного профиля. Отдельная калибровка такого операционного порога на независимых полных профилях пока не проведена. Качество энкодера и ошибки готового поиска поэтому оцениваются отдельно; метрики qrels не доказывают надёжное отклонение всех посторонних запросов в приложении.

## Кодирование длинных описаний

Политика task-v2 находится в `ml/common.py` и записывается в `metadata.json` как `encodingPolicy`:

- окно до **256 токенов**, включая специальные токены;
- соседние окна перекрываются на **64 токена**;
- из каждого окна извлекается CLS-вектор и нормируется по L2;
- векторы окон усредняются, после чего итог снова нормируется по L2.

Политика применяется внутри каждой секции и к запросу. Поэтому текст длиннее первого окна не отбрасывается целиком после 256 токенов. Усреднение окон всё равно может ослабить короткую важную задачу внутри длинной секции; это проверяется отдельно функциональными сценариями, а не считается решённым для любых текстов.

SHA-256 весов и политика кодирования образуют `encodingFingerprint`. Версия модели включает этот отпечаток: изменение длины окна, перекрытия или агрегации должно менять версию даже при прежних весах. Версия индекса дополнительно учитывает политику секций. В SQLite пакет векторов хранится вместе с версией индекса и хешем профессионального текста.

У старых артефактов сохраняется их исходная политика: CLS, L2 и обрезка до 192 токенов. Сравнение со старой локальной моделью поэтому относится ко всему поисковому решению, включая кодирование текста, а не только к изменению весов.

## Корпус task-v2 и разметка

`ml/dataset_v2.py` содержит авторский синтетический корпус `authored-task-retrieval-v2`: **84 семейства задач**, **168 описаний профилей** и **252 запроса с положительными ответами**. Дополнительно есть **24 посторонних запроса**, по восемь на часть. Всего — 276 запросов с учётом этих контролей. Персональных данных, реальных резюме и результатов найма в корпусе нет.

Корпус покрывает 14 направлений: Frontend, Backend, Fullstack, Mobile, DevOps, Security, ML, DataAnalysis, DataEngineering, QA, UXUI, BusinessAnalysis, ProductManagement и Embedded. В каждом направлении шесть семейств: четыре для train, одно для dev и одно для test. Семейство содержит два разных описания одной профессиональной задачи и три формулировки потребности работодателя.

Каждый положительный запрос содержит `relevant` — два конкретных ID подходящих описаний. Это явная авторская разметка релевантности документов, или qrels. Другие описания, в том числе той же профессии, не становятся положительными автоматически. Посторонний запрос имеет пустой список релевантных документов.

| Часть | Семейства | Новые описания этой части | Положительные запросы | Посторонние запросы | Документы в поисковом корпусе |
|---|---:|---:|---:|---:|---:|
| Train | 56 | 112 | 168 | 8 | 112: только train |
| Dev | 14 | 28 | 42 | 8 | 140: train + dev |
| Test | 14 | 28 | 42 | 8 | 168: train + dev + test |

Единица разделения — **целое семейство задачи**. Оба описания и все три запроса семейства принадлежат одной части. ID и нормализованные полные тексты проверяются на уникальность. Dev и test удерживают новые семейства, но все 14 профессий известны при обучении: эксперимент проверяет перенос на новые задачи внутри известных направлений, а не распознавание неизвестных профессий.

В dev и test присутствуют ранее виденные описания train как отвлекающие документы. На test нужно найти два подходящих описания среди всех 168, включая близкие задачи той же профессии. Это более строгая проверка, чем выбор единственного представителя направления из 14 документов.

Разметка создана командой и не подтверждена независимыми экспертами. Корпус открыт в исходном коде: отделение test от обучения защищает процедуру конкретного запуска, но не делает эксперимент независимым или слепым. Синтетические формулировки и небольшой размер набора ограничивают перенос результатов на реальные вакансии и кандидатов.

## Обучение и выбор порога

`ml/train.py` использует только train-запросы и train-описания для обучения и выбора отрицательных примеров. Для каждой связи запроса с одним из двух положительных описаний строятся три сравнения:

- с близким, но нерелевантным описанием **той же профессии**;
- с близким нерелевантным описанием другой профессии;
- с одним из посторонних train-текстов.

Сложные отрицательные примеры заново выбираются по текущему энкодеру перед каждой эпохой. Dev и test не участвуют в этом выборе. При текущем корпусе получается **1008 triplets за эпоху**. Функция потерь: `softplus(10 * (negative_similarity - positive_similarity + 0.15))`.

Параметры по умолчанию: AdamW, learning rate `2e-5`, weight decay `0.01`, clip norm `1`, batch `16`, seed `20261006`, 12 эпох и восемь CPU-потоков. Learning rate проходит 10% warmup и линейное снижение с нижним множителем 0.1. Фактические аргументы запуска, число шагов, параметры среды и время записываются в метаданные; значения по умолчанию не являются отчётом о завершённом запуске.

Checkpoint выбирается только по dev: сначала nDCG@5, затем MRR@10, затем средний отрыв лучшего положительного описания от самого близкого отрицательного. После выбора checkpoint порог косинуса определяется на всех dev-парах «запрос — документ» по F1, затем precision и recall. Порог не выбирается по максимальному баллу одного запроса и не настраивается на test или функциональном benchmark.

Пары включают положительные связи, нерелевантные задачи той же профессии, другие профессии и посторонние запросы. Поэтому даже принятый запрос может содержать ошибочно принятые отдельные документы. В оценке нужно показывать и качество ранжирования, и precision/recall порога, и принятие посторонних запросов.

## Оценка и границы результатов

На одном фиксированном test-корпусе сравниваются BM25 без ручного словаря синонимов, исходный RuBERT-tiny2 и дообученный task-v2. Для исходного и нового энкодеров используется одинаковая политика кодирования task-v2. Основные метрики: MRR@10, nDCG@5, Recall@5, Precision@5 и доля запросов с релевантным **документом** на первом месте. Совпадение профессии отдельно не засчитывается как релевантность задачи.

У каждого положительного запроса два релевантных документа; максимальный Precision@5 равен **0.4**. Посторонние запросы не входят в среднее метрик ранжирования положительных запросов и оцениваются отдельно. Порог фиксируется по dev до вычисления test. Измерения тёплого энкодера не включают запуск процесса, SQL, переиндексацию каталога, серверное ранжирование и сеть.

### Завершённые эксперименты энкодера

Task-v2 обучен за **349,217 с**: 12 эпох, 756 шагов AdamW, восемь CPU-потоков; по dev выбран checkpoint пятой эпохи. На удержанных 42 положительных запросах и восьми посторонних запросах среди 168 описаний получены следующие результаты. Каждое значение относится к конкретным релевантным описаниям задач.

| Метод на test task-v2 | MRR@10 | nDCG@5 | Recall@5 | Precision@5 | Релевантный документ первым |
|---|---:|---:|---:|---:|---:|
| BM25 | 0,669048 | 0,538581 | 0,571429 | 0,228571 | 0,571429 |
| Исходный RuBERT, политика task-v2 | 0,855385 | 0,717570 | 0,738095 | 0,295238 | 0,785714 |
| Локальный legacy, политика 192 токена | 0,835317 | 0,700447 | 0,738095 | 0,295238 | 0,761905 |
| Дообученный task-v2 | **0,884921** | **0,779607** | **0,809524** | **0,323810** | **0,809524** |

Порог task-v2 `0.4900432825088501` выбран на dev до просмотра test. На test точность отдельных принятых пар — **0,487805**, полнота — **0,714286**, F1 — **0,579710**: TP 60, FP 63, FN 24, TN 8253. В 39 из 42 положительных запросов принят хотя бы один релевантный документ; все восемь посторонних запросов отклонены. Низкая точность пар означает, что хорошие верхние позиции не исключают нерелевантных результатов ниже. В функциональном поиске по полным профилям отклонение посторонних запросов оказалось хуже; эти две проверки не подменяют друг друга.

Тёплый энкодер task-v2 при четырёх CPU-потоках: p50 **5,454 мс**, p95 **8,687 мс** для 42 коротких запросов. Для текста из 1886 символов: p50 **27,822 мс**, p95 **30,142 мс**, восемь повторов. Это измерения Python-кодирования; они не являются задержкой HTTP-поиска.

Дополнительно реально обучен task-v3: шесть эпох, learning rate `5e-6`, сохранение исходных эмбеддингов с весом 10, **115,389 с**, 378 шагов; выбран checkpoint четвёртой эпохи. Он использует прежние train-семейства, но **28 новых семейств dev/test** и новые посторонние запросы. Нормализованные тексты новых dev/test не повторяют прежний holdout. На новом test task-v3 получил nDCG@5 **0,841272**, Recall@5 **0,869048**, тогда как неизменённый task-v2 на том же новом test получил **0,855871** и **0,880952**. Task-v3 также чаще отбрасывает подходящие документы: принят релевантный ответ в 27 из 42 запросов. Поэтому task-v3 сохранён как проверенный эксперимент и не заменяет task-v2 в приложении.

Полные хеши, параметры, результаты и ограничения публикуются в [машиночитаемом отчёте](search_validation.json). Локальные исходные `evaluation.json` сохранены рядом с каждым неизменяемым артефактом. Оценки энкодера не описывают качество добавленного позднее этапа переранжирования и не доказывают точность найма на реальных данных.

Прежняя архитектура из `ml/dataset.py` использовала 56 семейств и релевантность по профессии; test содержал 14 документов и 42 положительных запроса. Исторический артефакт с префиксом `2a8b23a621e2` не является текущим локальным артефактом. Для фактического сравнения «до» отдельно обучена локальная legacy-модель за восемь эпох с идентификатором, оканчивающимся на `8517308064c1`. Этот старый корпус и его test уже были опубликованы, поэтому повторная оценка legacy не считается новым независимым holdout. Её результаты не сопоставляются напрямую с метриками task-v2 на другом корпусе.

### Функциональная проверка поиска

`ml/search-regression.mjs` проверяет поиск через настоящий `DirectoryService` с отдельной SQLite в памяти и синтетическим демонстрационным каталогом. Набор содержит **42 сценария**: 32 обязательных функциональных проверки и десять сложных сценариев, которые оцениваются отдельно. В нём есть переформулированные запросы по всем направлениям, ML без явного названия роли, объяснение электроники, неоднозначные потребности, нерелевантные запросы, отрицания, опечатки, длинные описания и ограничения города, зарплаты, стажа, языка и портфолио.

Для положительных семантических сценариев требуется и подходящая профессия, и ожидаемый конкретный профиль задачи в первых трёх результатах. Структурированные сценарии проверяют ожидаемые ID и соблюдение ограничений во всей выдаче, а для невозможных условий — пустой результат. Ошибки транспорта учитываются как ошибки, а не исключаются из знаменателя. Сравнение «до/после» требует одинаковых сценариев, каталога и выбранных ID; версия модели, её метаданные и хеши исходного кода записываются в отчёт. Проверка полного совпадения запросов с литералами трёх учебных корпусов не доказывает независимость формулировок по смыслу.

Этот набор не используется для настройки весов или выбора порога. Найденные ошибки используются для исправления продуктовых контрактов: обработки происхождения демонстрационных данных, состава профессиональных секций и разбора точных ограничений. Повторная успешная проверка известных сценариев показывает отсутствие этих регрессий; она не является новой независимой оценкой обобщения. Набор не заменяет test-корпус task-v2, экспертную разметку или исследование качества найма. Полные результаты и ошибки должны приводиться вместе, в том числе если обязательные проверки не прошли.

Фактический повторный прогон от **7 октября 2026 года**, на одном итоговом коде сервера, 140 вымышленных профилях и неизменных 42 сценариях:

| Артефакт | Пройдены сценарии | Ожидаемая задача в первых трёх, 29 запросов | Отклонены посторонние запросы |
|---|---:|---:|---:|
| Локальный legacy | 36/42 | 24/29 | 3/4 |
| Task-v2, косинус и исходный порог | 39/42 | 26/29 | 4/4 |
| Task-v2, совместная QDA-оценка и ограниченные ближайшие результаты | **42/42** | **29/29** | **4/4** |

В итоговой композиции пройдены 32 обязательных и десять сложных сценариев; транспортных ошибок нет. Ожидаемый конкретный профиль задачи первый в **27/29** запросов, профессия — в **28/29**. Семь запросов используют явно помеченную приблизительную выдачу, всего 19 профилей: результат 42/42 включает этот режим. Ожидания набора не менялись. Веса и численные пороги после просмотра этих сценариев не подбирались.

Промежуточные неудачные варианты также сохранены в отчёте: добавление только cross-encoder дало **33/42**, исправление контекста и охват всех фактических секций — **34/42**, строгая совместная LDA- или QDA-оценка — **35/42**. Они чаще оставляли подходящие запросы без результата. Политика ограниченных ближайших результатов, откалиброванная отдельно на dev, дала **39/42**, но ошибочно приняла три явно запрошенные внешние профессии. Общие правила профессиональной области исправили эти ошибки без изменения весов и порогов; их границы проверены на профессиях из разных отраслей, отрицаниях, альтернативах и запросах ИТ-продуктов для этих отраслей. Эти этапы выполнялись на разных версиях инженерного кода; их результаты показывают историю ошибок, а сравнение в таблице выше выполнено на одном итоговом коде.

Финальный локальный артефакт — `task-v2-search`, версия `rubert-tiny2-task-v2-ddbdd302d8d2-rank-cab2dda11d07`. Это результат проверки известных синтетических сценариев. Независимое качество на реальных резюме, новых формулировках и неизвестных профессиях остаётся непроверенным; универсальная «идеальная» работа не заявляется.

## Артефакты и защита эксперимента

Каждый запуск обучения создаёт отдельную папку в `server/data/semantic-runs/`. Она содержит веса и tokenizer, снимок `dataset.json`, копии исходного кода с хешами, историю выбора отрицательных примеров, `training-progress.json`, `metadata.json` и состояние запуска. После оценки рядом сохраняется `evaluation.json`.

`train.py` отказывается перезаписывать существующий запуск. Реестр `server/data/semantic-evaluations/` хранит факт оценки holdout по его содержимому: простая смена папки запуска или ID не должна разрешать дообучение после просмотра того же test. Повторная оценка неизменного артефакта возвращает сохранённый отчёт. Для последующей настройки после изучения ошибок требуется новый независимый набор удержанных задач, а не переименование прежнего.

Активная модель выбирается через `server/data/semantic-model/active.json`. Указатель можно переключить на другой готовый артефакт без перезаписи прежних весов и отчётов. Активация проверяет метаданные, SHA-256 весов и файлы второго этапа, калибровку и отпечаток всей композиции до атомарной замены указателя; worker повторно сверяет их при загрузке. Код обеспечивает неизменность через проверки команд, но не блокирует ручное редактирование файлов операционной системой.

Веса, tokenizer, HF cache, снимки запусков, базы и отчёты в `server/data/` исключены из Git. Legacy-модель для сравнения хранится отдельно в этой же игнорируемой области. Источник истины о реально активном артефакте — `active.json` и его `metadata.json`, а не исторический хеш в документации.

## Воспроизведение

Окружение текущего локального запуска: Python 3.12.10, PyTorch 2.12.0+cpu и Transformers 4.57.6; зависимости закреплены в `ml/requirements.txt`. Обёртка `scripts/ml.mjs` использует `.venv`, поэтому команды одинаковы для Windows и Linux. Подготовка окружения:

```powershell
npm run setup:search
```

На чистом checkout, до просмотра test этого корпуса:

```powershell
npm run train:search -- --output server/data/semantic-runs/task-v2 --dataset v2 --epochs 12 --threads 8
npm run evaluate:search -- --model server/data/semantic-runs/task-v2 --threads 4
npm run prepare:search-ranker
npm run calibrate:search-score -- --kind qda --output server/data/semantic-runs/task-v2-fused-qda
npm run prepare:search-policy
npm run check:search-model -- --model server/data/semantic-runs/task-v2-search
```

Оценка читает зафиксированный `dataset.json` из папки артефакта, поэтому ей не передаётся `--dataset`. Для сравнения legacy-модели на том же task-v2 корпусе дополнительно поддерживается `--reference-model <папка legacy-артефакта>`; её исходная политика кодирования сохраняется в отчёте. Обёртка автоматически активирует успешно обученный артефакт. Для уже готовой модели обучение следует пропустить. Явное переключение и запуск приложения:

```powershell
npm run activate:search-model -- server/data/semantic-runs/task-v2-search
npm run dev
```

Функциональная проверка конкретного артефакта, без HTTP-запросов и изменения базы приложения:

```powershell
node ml/search-regression.mjs --run --model server/data/semantic-runs/task-v2-search --output server/data/search-regression-after.json --compare server/data/search-regression-control-final.json --strict
```

`--strict` завершает команду с ошибкой при провале обязательных сценариев или ошибке транспорта; сложные сценарии остаются в отчёте. Сравнение требует заранее сохранённого отчёта «до» на тех же сценариях и каталоге. Без `--run` команда только проверяет структуру набора. Функциональные проверки можно повторять при исправлении сервера; это не разрешает подбирать веса или порог по результатам уже просмотренного научного test.

Прямой запуск worker для диагностики:

```powershell
.venv\Scripts\python -X utf8 ml/worker.py --model server/data/semantic-runs/task-v2-search --threads 4
```

На Windows при ограничении запуска PowerShell-скриптов используется `npm.cmd` вместо `npm`. На Linux путь к интерпретатору — `.venv/bin/python`. Ввод и вывод worker — UTF-8 JSONL. Запрос `{ "id": "q1", "texts": ["описание потребности"] }` получает `{ "id": "q1", "vectors": [[...312 чисел...]] }`. Health-запрос `{ "id": "h", "kind": "health" }` сообщает версию, политику кодирования и статус модели. При подключённом втором этапе запрос `{ "id": "r1", "kind": "rerank", "query": "описание потребности", "texts": ["роль\nописание задачи"] }` возвращает массив `scores` с исходными логитами. Допускается до 256 текстов по 12 000 символов, запрос переранжирования ограничен 1200 символами; пакет вычислений — 16 текстов. Стандартный вывод содержит только протокол, профессиональные тексты не логируются.

Детерминированные операции и фиксированный seed помогают воспроизвести процедуру, но не гарантируют побитовую идентичность весов между версиями PyTorch и оборудованием. Для каждого запуска сохраняются фактические хеши, версии среды и параметры.

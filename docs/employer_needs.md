# Потребности и рекомендованные категории

В кабинете «Кандидаты» кнопка «Потребности» открывает сохранённые описания команды. Можно создать потребность, изменить её, удалить или снова выполнить подбор. Сохранение сразу применяет задачи и условия; прежние именованные «Подборки» остаются доступными отдельно.

Потребность содержит название, описание команды, задачи и фильтры: специализацию, грейд, стек и дополнительные условия. Команда сохраняется как контекст проекта; текст задач поступает в смысловой поиск, а фильтры задают обязательные ограничения. Система не выводит недостающие роли команды автоматически из её описания.

## Хранение и права

В основном Node.js API потребности передаются как `state.hiringNeeds` через существующий `GET/PUT /api/platform/state`. В SQLite это отдельная таблица `platform_hiring_needs` с ключом `(owner,id)`, порядком и снимком полей. Потребность приватна, не публикуется как вакансия и доступна своему зарегистрированному работодателю. Кандидат и гость не могут создать её от имени работодателя.

Для записи нужны действующая сессия, `X-Platform-Identity` последнего чтения и актуальный `baseRevision`. Неверная идентичность или устаревшая версия возвращают `409`; неверная роль — `403`, отсутствие входа — `401`, некорректные поля — `400`. Изменения коллекций разных вкладок объединяются по ID; конкурентное изменение одной записи разрешается текущим механизмом объединения снимков, отдельного журнала версий потребности нет.

До 20 потребностей на владельца. Ограничения: ID до 100 символов, название до 200, команда до 2000, задачи до 1200. Нужны ID, название и хотя бы задачи, специализация либо стек. Фильтры проходят ту же проверку, что сохранённые поиски. Чужие поля, повторяющиеся ID и некорректные ограничения отклоняются атомарно. Старый клиент без поля `hiringNeeds` сохраняет существующие записи; явное `[]` удаляет их. Удаление кабинета каскадно удаляет его потребности; регистрационный аккаунт пока сохраняется, как указано в общем аудите.

## Рекомендации и выбор категории

`GET /api/directory/search` возвращает дополнительное поле `categories`. Категория — подтверждённая специализация и грейд доступных кандидатов, не предполагаемый грейд из резюме. Группы строятся после серверных проверок публикации, согласия, роли, условий, смыслового допуска и порядка профилей, до пагинации. Счётчик учитывает всю допущенную группу; `candidateIds` содержит до трёх примеров в итоговом порядке. Скрытые, отозванные и неподтверждённые профили не создают рекомендаций.

```json
{
  "specialization": "Embedded",
  "grade": "Middle",
  "count": 7,
  "demoCount": 0,
  "candidateIds": ["public-id-a", "public-id-b", "public-id-c"],
  "reason": "Причина соответствия описанию потребности и условиям",
  "approximate": false
}
```

Пример иллюстрирует контракт, не результат проверки реальных людей. При наличии смысловой части запроса категории упорядочены по лучшей исходной смысловой оценке внутри группы; тест и бонус ФСП не изменяют эту оценку. При пустом запросе или только распознанных условиях показаны доступные по фильтрам категории. Группа ближайших результатов помечена `approximate`; её причина не представляет совпадение как строгое. Если допущенных профилей нет, категории также пусты. Это группировка результатов действующего поиска, а не отдельная обученная модель классификации потребностей.

Общий каталог содержит также встроенные учебные профили, поэтому счётчик категории может включать демо. Их число возвращается в `demoCount` и названо в подсказке; карточки имеют пометку «Демо». При текущем порядке первая страница может состоять из учебных профилей: наличие реального кандидата нужно проверять по подходящим условиям и следующим страницам. Существующий порядок и право доступа к демокаталогу этим изменением не пересматриваются.

Выбор категории отправляет отдельный параметр `category` с JSON-объектом `{specialization,grade}`. Он сужает `items` и `total`, сохраняя исходные фильтры, запрос и полный список категорий. `selectedCategory` возвращает выбранное значение либо `null`. `offset/limit` относятся к выбранной группе; отсутствие `category` восстанавливает общую выдачу. Противоречие строгому фильтру даёт пустой список, а не ослабление условий. Применённая версия указана в `model.categoryRecommendationPolicy`.

Интерфейс показывает первые шесть групп и раскрывает остальные по кнопке. Категории работают со списком и режимом карточек. Во время нового запроса и при ошибке старые рекомендации скрыты; прежние кандидаты сохраняются с существующим сообщением об ожидании или ошибке. Запоздалый ответ не возвращает устаревшие категории.

Браузер ждёт ответ поиска до 120 секунд: холодная локальная модель загружается и индексирует профили дольше прежнего общего бюджета. Это предел ожидания, а не обещание скорости; варианты фильтров имеют прежний бюджет 30 секунд. Новый запрос отменяет старое ожидание в браузере. Серверные вычисления при этом могут продолжаться, поскольку worker и подготовка индекса общие для клиентов.

## Проверки и ограничения

- `npm run test:server`: хранение после перезапуска SQLite, разные владельцы и одинаковые ID, роли, идентичность, CAS, атомарность, удаление и совместимость старого клиента; группировка всей выдачи, подтверждённые категории, выбор и страницы, фильтры и отзыв публикации.
- `npm run test:hiring-needs`: реальный интерфейс и API в отдельной SQLite с почтой в памяти; сохранение, перезагрузка, изменение, переключение и удаление; две компании и два устройства, категории за пределами первой страницы, ошибки, поздние ответы, ожидание дольше прежнего бюджета с отменой, мобильная ширина и строгая доступность.
- `npm run test:browser`: полный зарегистрированный путь с настоящей обученной моделью; соответствие групп допущенным подтверждённым профилям, принадлежность примеров, выбор категории без изменения условий и сброс в общую выдачу. Также проверены контакты, согласия, мобильный интерфейс и восстановление.

В специальной проверке потребностей worker детерминированный; основной smoke использует настоящую локальную модель. Профили в обоих сценариях вымышленные и существуют только в их отдельных базах. Проверки подтверждают механику и права, не качество нейронной релевантности или профессиональную состоятельность грейда. Рекомендованные категории наследуют ограничения действующего смыслового поиска; независимая оценка полезности рекомендаций остаётся отдельной задачей.

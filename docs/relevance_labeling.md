# Протокол разметки релевантности подбора

Документ описывает, как размечен набор [ml/relevance-labels.json](../ml/relevance-labels.json), по которому считаются метрики подбора ([metrics_and_validation.md, раздел 14](metrics_and_validation.md#14-релевантность-подбора-размеченный-набор-и-метрики)), и как проверяется надёжность этой разметки.

## Что размечается

Пара «потребность работодателя — профиль кандидата». Потребностей 50 (по 3–5 на каждую из 14 специализаций), профилей 146: все вымышленные демопрофили каталога. Оценивается только профессиональное соответствие: описанная в профиле задача, роль и заявленный стек. Город, зарплата, грейд, результат теста и ФСП в оценку не входят: это условия и правила порядка, а не релевантность задаче.

## Шкала

| Оценка | Когда ставится |
| --- | --- |
| 3 | Описанная в профиле задача прямо решает потребность |
| 2 | Та же специализация; если в потребности названы технологии, у профиля есть хотя бы одна из них |
| 1 | Смежная специализация, та же специализация без названных технологий или частичное совпадение задачи из другой специализации |
| 0 | Не подходит |

Спорные случаи решаются в пользу меньшей оценки. Альтернатива «A или B» считается выполненной, если есть хотя бы одна технология.

## Первая разметка (эталон команды)

Выполнена командой до первого запуска оценки, 11 октября 2026 года. Для каждой потребности вручную выбраны профили с оценкой 3 (поле `exact`) и записаны ручные оценки 1 для частичных совпадений из других специализаций (`overrides`). Остальные оценки получены по правилам шкалы из специализации и стека профиля. Разметчик не видел выдачу подбора для этих потребностей. После первого запуска разметка не менялась.

Ограничение: оценки 2 и 1, выведенные из специализации и стека, используют те же сведения, что и подбор. Поэтому нужна независимая проверка.

## Вторая, независимая разметка

1. `node ml/relevance-agreement.mjs sheet --output server/data/relevance-agreement` формирует слепую таблицу из 300 пар: по 6 на потребность, со всеми уровнями эталонной шкалы, в случайном порядке с фиксированным seed. В таблице есть текст потребности, роль, стек и описание задачи профиля; эталонных оценок и результатов поиска нет.
2. Второй разметчик не участвовал в первой разметке и не видит ни `ml/relevance-labels.json`, ни выдачу. Он читает только этот документ и ставит оценку 0–3 в столбец `grade_0_3`. Обсуждать пары с автором первой разметки до сдачи таблицы нельзя.
3. `node ml/relevance-agreement.mjs score --sheet <таблица> --key server/data/relevance-agreement/key.json` считает согласие:
   - долю полного совпадения оценок и взвешенную каппу Коэна с квадратичными весами по шкале 0–3;
   - согласие и каппу по бинарной релевантности (оценка ≥ 2), на которой основаны P@5 и P@10;
   - согласие и каппу по точным совпадениям (оценка 3), на которых основан MRR@10;
   - матрицу расхождений.
4. Разметка считается надёжной при взвешенной каппе ≥ 0.6 и каппе по бинарной релевантности ≥ 0.6. Расхождения разбираются вместе после подсчёта; эталон меняется, только если ошибка в нём очевидна, и такие изменения перечисляются в отчёте вместе с пересчитанными метриками.

## Результат

Вторую разметку 11 октября 2026 года выполнил temurysega; оценки — [ml/relevance-second-labels.csv](../ml/relevance-second-labels.csv). Взвешенная каппа по шкале 0–3 — 0.80, по точным совпадениям — 0.86, по бинарной релевантности — 0.52 (ниже порога 0.6). Основное расхождение: второй разметчик ставит 1 вместо 2 профилям той же специализации с другой задачей. Подробности и выводы для метрик — в [разделе 14 отчёта о валидации](metrics_and_validation.md#надёжность-разметки).

Повторить подсчёт: `node ml/relevance-agreement.mjs sheet --output server/data/relevance-agreement`, затем `node ml/relevance-agreement.mjs score --sheet ml/relevance-second-labels.csv --key server/data/relevance-agreement/key.json`.

## Правила v2 и отложенный набор

Вторая разметка показала, что правило оценки 2 в версии 1 слишком мягкое: одинаковая специализация и одна общая технология давали «подходит», даже когда рабочая задача другая (каппа по бинарной релевантности 0.52 при пороге 0.6). Поэтому для итоговой оценки введена версия 2 шкалы:

| Оценка | Когда ставится (v2) |
| --- | --- |
| 3 | Описанная в профиле задача прямо решает потребность |
| 2 | Близкая рабочая задача: профиль делал работу того же рода и с небольшой адаптацией решит потребность. Одна только специализация или технология оценку 2 не даёт |
| 1 | Та же или смежная специализация с другой задачей, либо частично полезный профиль другой специализации |
| 0 | Не подходит |

Набор версии 1 (50 потребностей) просмотрен при разработке и остаётся набором разработки. Для итоговой оценки создан отложенный набор [ml/relevance-labels-holdout.json](../ml/relevance-labels-holdout.json): 42 новые потребности, по 3 на каждую специализацию, с формулировками, которых нет в наборе разработки. Оценки 3 и 2 (поля `exact` и `close`) и частичные совпадения (`partial`) выбраны вручную по текстам задач профилей и закоммичены до первого запуска подбора на этих потребностях. После этого ни подбор, ни пороги, ни разметка по отложенному набору не настраиваются.

Вторая разметка отложенного набора выполняется так же вслепую: `node ml/relevance-agreement.mjs sheet --labels ml/relevance-labels-holdout.json --output server/data/relevance-agreement-v2`, оценки — по шкале v2, подсчёт согласия — командой `score` с тем же ключом `--labels`.

Результат: вторую разметку v2 вслепую выполнил temurysega, оценки — [ml/relevance-second-labels-holdout.csv](../ml/relevance-second-labels-holdout.csv). Взвешенная каппа 0.91, по бинарной релевантности 0.77 (по правилам v1 было 0.52), по точным совпадениям 1.00; все показатели выше порога 0.6.

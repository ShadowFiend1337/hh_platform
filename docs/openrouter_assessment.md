# OpenRouter для открытых заданий

Статус на 9 октября 2026 года: изолированный серверный адаптер для авторской проверки и предварительного контекста открытых заданий. Он не меняет подтверждённые категории и не присваивает грейд. Модели для помощников и генерации тестовых вопросов описаны в [llm_usage.md](llm_usage.md).

По умолчанию используется самая дешёвая открытая instruct-модель каталога OpenRouter `qwen/qwen3-30b-a3b-instruct-2507` (веса Apache-2.0). Явно допускаются также `qwen/qwen3-32b`, `qwen/qwen3.8-27b` и `deepseek/deepseek-v3.2` (MIT). Это проверка доступного контракта, а не доказательство качества оценивания.

## Выбор открытой модели

[Письменное уточнение организаторов](specifications/Ответы%20на%20вопросы%20трек%20ФСП%20ЛЦТ__.xlsx), первый лист, B7 (VS.3), разрешает зарубежные облачные LLM и предпочитает открытые модели с адекватным числом параметров. Поэтому в проекте допускаются только модели с опубликованными весами: Qwen (Apache-2.0) и DeepSeek (MIT).

Альтернатива `qwen/qwen3.8-27b` — более крупная модель того же семейства с [опубликованными весами](https://huggingface.co/Qwen/Qwen3.8-27B). Её стоит выбирать, если на эталонных ответах дешёвая модель окажется недостаточной.

Открытые веса, бесплатный инференс и российское размещение сервиса — разные свойства. Использование Qwen через зарубежный API не делает обработку локальной. Для авторской проверки достаточно задачи, рубрики и обезличенного ответа; полное резюме для неё не требуется.

Публичные показатели кодирования и рассуждений у моделей получены на разных наборах и с разными настройками. Нужна одинаковая проверка моделей на утверждённых ответах правильного, частичного и ошибочного уровня, допустимых альтернативах, противоречиях и инструкциях внутри ответа. Согласие двух LLM не заменяет эталон.

## Конфигурация

Только серверные переменные окружения:

```dotenv
OPENROUTER_API_KEY=<локальный ключ, не коммитить>
OPENROUTER_ASSESSMENT_MODEL=qwen/qwen3-30b-a3b-instruct-2507
```

Ключ остаётся серверным. Допускаются только перечисленные открытые модели; другие идентификаторы, включая суффиксы `:free` и датированные версии, отклоняются.

При отсутствии ключа создание адаптера допустимо, `configuration().configured` равно `false`, попытка вызвать проверку завершается ошибкой конфигурации. Пустой или посторонний идентификатор модели отклоняется; автоматической замены модели нет. При недоступности выбранной модели адаптер возвращает ошибку. Он не делает запросов при импорте, создании или чтении `configuration()`.

Ключ передаётся только заголовком Authorization на фиксированный HTTPS endpoint OpenRouter. Произвольный URL из конфигурации не принимается, редиректы запрещены. `configuration()` содержит только модель, признаки настройки и технические лимиты. Ключ, тело запроса, ответ кандидата и исходная ошибка провайдера в объект ошибки или журнал не записываются.

## Серверный контракт

Модуль: [open-assessment-provider.mjs](../server/open-assessment-provider.mjs). Фабрика `createOpenAssessmentProvider({ env, fetchImpl, timeoutMs, maxRetries, maxRetryDelayMs })` позволяет подставить транспорт для автономной проверки. `env` по умолчанию — окружение процесса; файл `.env` сам адаптер не читает.

| Метод | Результат |
| --- | --- |
| `configuration()` | Безопасные настройки без секретов; `experimental: true`, `approvedForCertification: false` |
| `evaluateDraft({ question, answer }, { signal })` | Критерии одного открытого ответа, идентификаторы задания и версии банка/рубрик; `purpose: author-preview-evaluation` |
| `generateVariantPreview({ question, context }, { signal })` | Неоцениваемый текст для редактора; `purpose: author-variant-preview`, обязательная редакторская проверка |

`question` обязан поступать из приватного банка на сервере, например из `getOpenProgram()`. Браузер не должен присылать рубрику, эталон, грейд, критические ошибки или ограничения персонализации. Адаптер проверяет форму и выделяет разрешённые поля, но сам факт передачи объекта не подтверждает его происхождение. Его публичная API-маршрутизация отсутствует; будущий обработчик должен находить вопрос по сохранённой серверной попытке. Эталоны и оценки черновиков нельзя отдавать кандидату вместе с вопросом.

В запрос оценивания входят условие, серверная рубрика с якорями 0–3, допустимые альтернативы, критические ошибки и один ответ. Полное резюме, контакты, достижения ФСП, название аккаунта, стаж и иной профиль не нужны. Ответ рассматривается как недоверенный текст, включая возможные инструкции внутри него.

Структура одного критерия:

```json
{
  "criterionId": "atomicity",
  "status": "scored",
  "score": 2,
  "evidence": ["Транзакция связывает изменения."],
  "rationale": "Назван способ связать изменения согласно якорю рубрики.",
  "needsReview": false
}
```

Это пример контракта, не оценка настоящего кандидата. Обязателен ровно один элемент для каждого серверного `criterionId`; неизвестные, повторяющиеся или пропущенные критерии отклоняются. `score` — целое 0–3. Для непроверяемого критерия используется `status: not_assessable`, `score: null` и `needsReview: true`; это не ноль. Положительная оценка требует буквального непустого фрагмента именно ответа. Каждая цитата проверяется через точное вхождение в ответ без исправления регистра или пробелов. Выдуманная цитата и цитата только из эталона отклоняются.

Отсутствие действия может быть записано как ноль без цитаты, но сервер принудительно помечает такой вывод для проверки. Пустой ответ не получает положительные свидетельства. Общий `needsReview` не может скрыть неопределённость отдельного критерия. Наличие цитаты подтверждает происхождение фрагмента, но не доказывает правильность смысловой оценки; для этого нужны эталоны и содержательная проверка.

Модель не возвращает и не вычисляет `passed`, подтверждённый грейд или итоговый процент. Дополнительные поля такой формы отклоняются. Если модель сообщает неопределённость, она остаётся видимой для последующего серверного решения. Все результаты этого адаптера имеют `approvedForCertification: false`. Преобразование критериев в итог, правила продолжения, обработка противоречий и история попыток относятся к отдельной будущей реализации.

В исходном авторском банке предметные якоря частично общие внутри семейства, а условия выбранного уровня выделены отдельно. Новые направления содержат предметные рубрики по каждому грейду; компилятор передаёт их и разбор соответствующего уровня, а не эталон Middle для всех. Такая запись не означает, что рубрика независимо подтверждена для каждого грейда. До предметной проверки и эталонной разметки по уровням результат адаптера остаётся экспериментальным даже при корректной JSON-структуре и буквальных цитатах.

## Предварительная персонализация

Генератор получает семейство, исходное условие, выбранный уровень, неизменяемые ограничения и короткий подготовленный сервером контекст. Из `context` передаются только разрешённые самим семейством поля из перечня `domain`, `entityNames`, `projectContext`, `stack`, `dataLabels`, `companyContext`. Остальные поля игнорируются. Строки и списки ограничены по длине; `projectContext` — до 1000 символов. Контекст должен описывать обезличенную профессиональную ситуацию. Название разрешённого поля не делает помещённые в него персональные данные безопасными; серверный вызывающий код должен подготовить его заранее.

Выбранная модель выдаёт только `contextIntroduction` — вступление до 800 символов. Адаптер не разрешает модели переписывать основной текст, числовые ограничения, якоря, эталон или уровень: `basePrompt` сохраняется побуквенно, вступление добавляется отдельно. Эталон и рубрика генератору не передаются. Полученный текст требует редакторской проверки на подсказки, противоречия и новые скрытые ограничения. Он не становится автоматически новым банковским вариантом и не включается в зачётную попытку. Это подготовка узкого предварительного контекста, а не законченный генератор валидированных равнозначных вариантов.

## Ответ провайдера и ошибки

Применяется `response_format: json_schema` с `strict: true`, а в предпочтениях провайдера — `require_parameters: true` и `allow_fallbacks: false`. Сервер повторно проверяет полученный JSON: поддержка структурированного ответа зависит от конкретного endpoint и сама по себе не заменяет проверки. [Документация структурированных ответов](https://openrouter.ai/docs/guides/features/structured-outputs).

Запрос содержит одну выбранную модель. Ответ должен содержать точный выбранный идентификатор; ответ другой модели отклоняется. Ответ с отказом, обрывом, превышением длины или неправильным JSON не становится оценкой. Проверяется и поле `error` внутри HTTP 200 — такие ошибки возможны после принятия запроса провайдером. [Ошибки OpenRouter](https://openrouter.ai/docs/api_reference/errors-and-debugging).

По умолчанию вся операция, включая чтение и ожидание повтора, ограничена 30 секундами; максимум настройки — 60 секунд. Внешний `AbortSignal` отменяет запрос и ожидание повтора. Ответ провайдера ограничен 200 000 байт. Сетевой сбой или HTTP 429/502/503/504 допускает один повтор, настройка — не более двух. Короткий `Retry-After` соблюдается. Если заявленное ожидание превышает предел 1,5 секунды, автоматического раннего повтора нет: возвращается временная ошибка для последующей повторной проверки. Ошибки запроса, ключа, оплаты или прав автоматически не повторяются. Сетевой повтор может привести к дополнительному платному вызову, если первый запрос дошёл до провайдера; лимит повторов не является платёжной гарантией.

Каждая нормализованная ошибка имеет `needsReview: true`; технический сбой не возвращает кандидатский провал, не изменяет грейд и не списывает пересдачу. Будущий серверный маршрут должен сохранить ответ кандидата и поставить его в ожидание повторной оценки. Сейчас такого маршрута и очереди нет.

Предпочтение `data_collection: deny` ограничивает маршрутизацию согласно заявленным правилам провайдера. Это не обещание отсутствия любого хранения у всех участников: настройки OpenRouter и условия конкретного поставщика необходимо проверить перед передачей настоящих ответов. [Настройки маршрутизации](https://openrouter.ai/docs/guides/routing/provider-selection), [правила сбора данных OpenRouter](https://openrouter.ai/docs/guides/privacy/data-collection).

## Что проверено

```powershell
node --test server/tests/open-assessment-provider.test.mjs
```

Автономные проверки используют только mock-транспорт: валидация критериев и буквальных цитат, явная неопределённость, ограниченная генерация, таймауты, отмена, лимиты, повторы, ошибки HTTP и отсутствие секретов в возвращаемых ошибках. Ни настоящий ключ, ни платный вызов, ни реальные резюме для этих тестов не используются.

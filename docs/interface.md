# Интерфейс predel

## Статус и источники

Обновлено 11 октября 2026 года. Интерфейс predel реализует сценарии [ТЗ](specifications/ФСП%20спец.%20трек%20ТЗ.pdf): кабинеты кандидата, работодателя и модератора, анкету, экзамен, поиск, приглашения, вакансии, отклики и задания. Он работает с основным Node.js API и серверной SQLite. Проверки и результаты описаны в [валидации тестирования](assessment_validation.md), [метриках подбора](metrics_and_validation.md) и [проверках резюме](resume_validation.md).

Архив `backend.zip`, предоставленный отдельно на рабочем столе, содержит FastAPI-сервис генерации презентаций: загрузку шаблонов, задания сборки, превью и экспорт через `/v2/templates` и `/v2/decks`. В нём нет API профилей кандидатов, тестирования и подбора. Для интерфейса переиспользованы его React-зависимости, lockfile, TypeScript-настройки, локальные шрифты и дизайн главной страницы с оригинальным изображением брелоков. Сохранены плавающая шапка, композиция, синий акцент, анимации и адаптивные размеры; тексты и примеры заменены на сценарии подбора специалистов. Сам презентационный backend не включён.

Логотип ФСП извлечён из `ppt/media/image9.png`, а полоса партнёрских логотипов — из верхней части `ppt/media/image11.png` предоставленного [шаблона презентации](specifications/ЛЦТ_2026_Шаблон%20презентации%20ФСП.pptx). Состав и пропорции логотипов сохранены.

## Тестирование и данные

В закрытом банке 1680 вариантов задач: 70 программ, 420 семейств, три темы, по одному базовому и прикладному семейству на тему, четыре содержательных варианта каждого семейства. Все пять грейдов имеют свои программы; тест Middle не подтверждает Senior или Lead. Попытка содержит шесть заданий с одинаковыми весами и бюджетом авторской сложности 9. Сервер исключает варианты последних двух попыток владельца: зарегистрированный аккаунт сохраняет эту связь при повторном входе и на другом устройстве, гостевой владелец связан с cookie. Остаётся минимум два варианта каждого семейства, что исключает принудительный цикл из трёх наборов. Задания и ответы перемешиваются и получают непрозрачные ID. Сервер выдаёт только задания конкретной попытки; ключи остаются на сервере. Вариант фиксируется до начала и проверяется по сохранённому снимку. Порог 70/100, программа и 30 минут показаны заранее.

Описание вакансии сопоставляется с явным словарём навыков и тегами задач. Приоритет влияет на выбор содержательного варианта и порядок тем, сохраняя обязательное ядро и веса. Совпадения относятся к выбранным задачам; распознанные, но не проверяемые требования показаны отдельно. Это прозрачный лексический разбор, не ML и не полный анализ всех требований. Отдельная публикация вакансии реализована, но для приглашения она по-прежнему не требуется.

[Автоматический отчёт](assessment_validation.md) проверяет структуру вариантов и отсутствие закрытого банка в собранном клиенте. Фактическая сопоставимость сложности и валидность профессионального грейда ещё не проверены на участниках; авторские метки сложности не заменяют калибровку.

Каталог и кабинеты требуют регистрации с подтверждением почты и входа. «Попробовать» и прямая ссылка на `/app` без сессии открывают регистрацию; гостевой браузер не читает и не сохраняет рабочее состояние. API также отклоняет гостевые обращения. Обычный работодатель видит опубликованные профили зарегистрированных кандидатов и встроенный вымышленный каталог с меткой «Демо» для чтения. Завершённые анкеты без подтверждённого грейда доступны ниже подтверждённых профилей с явной самооценкой; фильтры подтверждённого грейда и рекомендации категорий не принимают её за результат теста. На главной показаны статичные примеры без имён людей. Собственный новый профиль начинает без подтверждённого грейда, приглашений и истории тестов; локальные аккаунты команды содержат отдельно обозначенные учебные фикстуры и изолированы от обычных пользователей. Софт-скиллы доступны как необязательная самооценка: импорт объединяется с ручным выбором, значения сохраняются в профиле и анкете. Сопоставимость вариантов теста необходимо проверить по [плану валидации](metrics_and_validation.md).

Основной Node.js API хранит аккаунты, ожидающие регистрации, сессии, попытки и результаты, профиль, компанию, анкеты, подборки, приглашения, вакансии, отклики, события согласий и внешние подтверждения в SQLite. Модули используют общее соединение для удаления данных аккаунта в одной транзакции. `localStorage` хранит копию состояния для браузера; текущий поиск и указатель незавершённого теста — в `sessionStorage`. Версия снимка проверяется сервером: устаревшая запись получает 409. Успешные результаты извлекаются из серверных попыток своего владельца; клиент не может присвоить себе чужой грейд или достижение ФСП.

Демокаталог не открывает гостевой доступ: без сессии рабочий API возвращает `401`, а роль кандидата не получает поиск других людей (`403`). Сервер вычисляет `demoProfile` только для встроенных синтетических записей без владельца; случайный `synthetic` или старый гостевой профиль не дают этой возможности. «Демо» видно в списке, карточках и подробностях, а PDF сообщает вымышленное происхождение. Кнопка приглашения отсутствует и сервер отдельно отклоняет её вызов. Отправлять предложения и раскрывать контакты можно только в проверяемом взаимодействии зарегистрированных участников; учебная локальная пара остаётся изолированной от обычных пользователей и общего демокаталога.

[HTTP-проверка демокаталога](../server/tests/demo-catalog-access.test.mjs) и [браузерный сценарий](../frontend/tests/demo-catalog.mjs) подтверждают доступ нового работодателя, фильтры, карточки и PDF, сохранение избранного при повторном входе, запрет недоверенных связей и изоляцию локальных аккаунтов. Они работают на отдельных базах с почтой в памяти и детерминированным worker; положительный ответ смыслового поиска здесь проверяет интерфейс и область доступа, а не качество модели. Прежние автономные ML-эксперименты не проходили авторизованный HTTP-каталог. Массовый импорт чужих наборов профилей пока не реализован; способ загрузки закрытого набора жюри не предоставлен.

Отдельный проход с настоящим локальным `SemanticWorker` через регистрацию, сессию и HTTP-поиск также прошёл в изолированном сервисе: вымышленные профили вернулись с меткой демо и пустыми контактами. Это техническая проверка доступности действующего модельного пути, не независимая оценка подбора. Рабочая база и внешняя почта не использовались.

Парсер возвращает массивы работы, pet-проектов, достижений и интересов. Форма сохраняет их в JSON профиля и нового снимка анкеты; Node.js и FastAPI проверяют типы и лимиты. История, карточка работодателя, свайп, готовность профиля, поиск и PDF читают эти разделы с поддержкой старых текстовых записей. Отрасль в анкете не выбирается: направление задаётся специализацией. Закрытые контакты вычищаются из вложенных описаний публичной карточки и PDF. Снимок анкеты нельзя заменить или удалить обычным PUT; изменения создают новый ID. Старые записи без доступной анкеты не восстанавливаются из текущего профиля.

Ручной ID ФСП не получает подтверждённую историю. Отдельная сессионная демопривязка получает вымышленные записи от сервера и поддерживает пустую/отозванную историю; карточка, подробности и PDF сохраняют учебное происхождение. После объединения доступны также настраиваемый OIDC-адаптер, публичные результаты с проверкой принадлежности модератором и другие внешние источники. Это реализованная механика, но настоящий API ФСП и реальные внешние аккаунты в объединительном прогоне не проверялись. Прямой PDF-экспорт не превращает учебную запись в проверенное достижение.

Смысловой подбор использует локальный RuBERT-tiny2, дообученный на авторских синтетических профессиональных задачах. Каждая секция профиля кодируется отдельно в нормированный вектор из 312 чисел: описание задач, история работы, достижения, образование и роль со стеком. Распознанные отрицания собственного опыта и планы будущего обучения удаляются из модельного текста, исходные поля профиля остаются видимыми. Секции ограничены 4000 символами, весь профиль — 12 000 символов. Энкодер обрабатывает текст окнами по 256 токенов с перекрытием 64 и усредняет нормированные векторы окон. Имя и контакты не входят в профессиональные векторы. Версия модели, политика индекса `positive-structured-profile-sections-max-v4` и SHA-256 секций сохраняются в SQLite; старые векторы пересчитываются.

RuBERT выбирает короткий список до 50 профилей. Локальный mMARCO cross-encoder оценивает запрос и фактические профессиональные секции, а калибратор объединяет два сигнала одной секции. У профиля без исходных описаний о себе и работы дополнительно оцениваются роль и навыки; образование или достижения не мешают этой проверке. Если побеждает такая секция, объяснение говорит «Роль и навыки в профиле», API возвращает `evidenceKind: "competencies"`. Для неё требуется строгий порог; приблизительный допуск, настроенный на описания задач, на роль и стек не переносится. Выдача показывает секцию с максимальной итоговой оценкой. Пара второго этапа ограничена 512 токенами; часть длинного описания может отсечься. Если строгих результатов нет, допускаются максимум три приблизительных профиля с победившей профессиональной секцией и общей подписью.

Для узкого списка явно названных профессиональных методов сервер проверяет исходные положительные сведения отдельно от нейронной оценки: штрихкод не подменяет NFC, а пароль — аппаратный аутентификатор. Учитываются перечисленные синонимы, альтернативы «или», обязательные сочетания и необязательные требования. Вводный запрос о найме без заголовка, выделенная задача и профессиональные требования сохраняются; описание компании и условий не добавляет методы к профессиональной задаче. Исходные профессиональные поля проверяются полностью в пределах валидации, чтобы обрезка модельной секции не меняла смысл отрицания. Роль со стеком не перекрывает явное отрицание того же метода в фактических сведениях. Проверка повторяется после ожидания модели и действует для строгих и приблизительных результатов; поиск без текста использует SQL-фильтры.

API сообщает правила сервера в `model.profileEvidencePolicy: "structured-professional-sections-with-strict-sparse-competencies-v3"` и `model.taskEvidencePolicy`, отдельно от закреплённой калибровки. Явная профессия в запросе или фильтрах не разрешает приблизительный допуск секции роли и навыков. Формула модели и пороги сохраняются; оценка не означает вероятность успешного найма или подтверждение грейда. Качество новой политики нельзя вывести из прежних метрик обучения. [Техническое описание](semantic_model.md) содержит архитектуру и команды запуска. Полный авторский контроль выявил смысловые ошибки; независимая проверка на реальных потребностях и профилях ещё необходима. При недоступности модели текстовый запрос сообщает ошибку сервиса.

## Условия работы и границы реализации

Регистрация и вход связывают HttpOnly-сессию аккаунта с постоянным владельцем данных. Код подтверждается до создания аккаунта; доставка настоящего письма требует SMTP. Без SMTP локальный код находится в `server/data/mail.log`. Восстановление пароля через интерфейс не реализовано. Результаты подбора на размеченных потребностях и условия эксперимента опубликованы в [метриках валидации](metrics_and_validation.md#14-релевантность-подбора-размеченный-набор-и-метрики).

SMTP-доставка ранее проверена через AuthService в отдельной базе: пользователь получил письмо, код подтвердил тестовый аккаунт, повторный вход прошёл. Для каждого окружения SMTP настраивается отдельно; секреты в Git не хранятся.

Поле ФСП ID не создаёт проверенные достижения: доступна отдельная привязка источника и импорт результатов с указанием происхождения. Публикация вакансий, самостоятельные отклики и [регулярные задания](employer_tasks.md) подключены к основному API и интерфейсу: работодатель назначает задание, кандидат отвечает, сервис сохраняет ИИ-разбор и решение работодателя, принятое задание обновляет отметку актуальности профиля. Софт-скиллы собираются необязательным полем и показываются как самооценка.

Браузерные сценарии [PDF](../frontend/tests/profile-pdf.mjs), [истории](../frontend/tests/history.mjs), [анкеты](../frontend/tests/resume-form.mjs) и [профиля после провала](../frontend/tests/unconfirmed-directory.mjs) используют изолированный сервис с зарегистрированными аккаунтами. Результаты проверок импорта и их ограничения указаны в [проверке резюме](resume_validation.md).

Дополнительный FastAPI backend запускается отдельными командами и использует другую базу. Его текстовый поиск и набор эндпоинтов не повторяют основной Node.js API; встроенный демокаталог в нём по-прежнему исключён. Исправление доступа и проверки выше относятся к основному Node.js серверу; переключать runtime без проверки этих отличий нельзя.

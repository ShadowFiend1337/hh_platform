# Внешние источники и доказательства навыков

## Реализованный объём

Модуль работает в **основном Node.js backend**. Он предоставляет API подключения источников, SQLite-хранение, очередь фоновой синхронизации, OIDC-проверку владельца, серверные доказательства и подписанный входящий webhook. В FastAPI эти маршруты не перенесены; базы двух серверов не синхронизируются.

Контракты:

- [API модуля внешних подтверждений: integrations.openapi.json](api/integrations.openapi.json). Доступен также на `GET /api/integrations/openapi.json`; остальных маршрутов основного Node.js API он не описывает. Для сессионного демосценария действует отдельный [контракт ФСП](fsp_integration.md).
- [Предлагаемый ресурсный API ФСП: fsp-provider.openapi.json](api/fsp-provider.openapi.json). **Это предложение команды, а не официальный опубликованный контракт Федерации.**
- Внутренний интерфейс провайдера приведён ниже.

Основной HTTP-сервис предлагает конфигурируемый `fsp`, Codeforces, AtCoder, Kaggle и GitHub. Сессионный `fsp-demo` сохранён в отдельном строгом сервисе и не предлагается как провайдер общего подключения. Для GitHub требуется настройка собственного OAuth-приложения; официальный доступ к ФСП пока не получен. hh.ru не подключён. Сведения резюме и репозиториев нельзя автоматически объявлять подтверждённым профессиональным грейдом.

Доступен также [пилот поиска по публичным протоколам ФСП](fsp-public-research.md): локальный OCR официального PDF, проверенный каталог и отдельный endpoint поиска по ФИО. Он не требует доступа к API Федерации и не подтверждает принадлежность записи кандидату.

Дополнительно реализованы [привязка результатов и модерация](achievement-moderation.md): приватные материалы, отдельное серверное право модератора, решения с версиями/аудитом и проверка хеша официального PDF. Одобренная принадлежность публичной записи имеет `verificationMethod=manual_review`; это не OIDC-привязка ФСП ID.

## Поток данных

1. Зарегистрированный кандидат сохраняет профиль с согласием на обработку данных.
2. В разделе «Внешние подтверждения» отдельно соглашается на получение и хранение достижений из выбранного источника.
3. `POST /api/integrations/{provider}/connect` начинает предусмотренную источником проверку: авторизацию, challenge в публичном профиле либо проверку собственного токена кандидата.
4. OIDC-адаптер ФСП использует Authorization Code, PKCE S256 и nonce. После проверки ID token устанавливается связь с внешним аккаунтом. Остальные способы описаны в документах соответствующих провайдеров.
5. Сервер создаёт долговечную задачу синхронизации. Worker получает полный снимок, проверяет владельца и формат каждой записи.
6. После полной проверки транзакция обновляет доказательства, состояние задачи и фильтр ФСП в каталоге. Частичные результаты не публикуются.
7. Кандидат видит свои доказательства; зарегистрированный работодатель видит публичные записи доступного опубликованного профиля по действующим правилам каталога и согласия. Доказательство источника не превращает самооценку грейда в подтверждённую категорию. В карточке показаны источник, статус, дата проверки и индивидуальное/командное участие.

Контакты кандидата не входят в контракт внешних доказательств. Текстовые названия, результаты и роли очищаются от распознанных email/телефонов. Произвольные дополнительные поля внешнего ответа не публикуются. Ссылка источника допускает только HTTPS без учётных данных и query.

## Внутренний контракт адаптера

Реестр `createProviders` находится в `server/integrations/providers.mjs`. Ниже приведена базовая часть контракта OIDC-провайдера и внутреннего демопровайдера; challenge, API-token и GitHub OAuth имеют собственные методы, описанные в документах этих источников:

```ts
interface EvidenceProvider {
  id: string;
  name: string;
  mode: 'live' | 'demo';
  auth: 'oidc' | 'demo';
  enabled: boolean;
  authorize(input: {
    state: string; nonce: string; challenge: string;
  }): Promise<string>; // live: URL авторизации
  exchange(code: string, pending: {
    verifier: string; nonce: string;
  }): Promise<{
    subject: string; externalId: string;
    identityVerified: boolean; credentials: object;
  }>;
  load(connection: {
    id: string; subject: string; externalId: string;
    credentials: object;
  }, persistCredentials: (value: object) => void): Promise<{
    subject: string; externalId: string;
    achievements: SourceAchievement[];
  }>;
}
```

`SourceAchievement` соответствует `Achievement` из предлагаемого OpenAPI ФСП.

Внутренний демопровайдер вместо OIDC использует `connect(owner, scenario)` для изолированных проверок сервиса. Его общий контракт не смонтирован на основной HTTP-маршрут `fsp-demo`: там действует сессионный сервис с обязательным `baseRevision`. Callback предусмотрены для `fsp` и GitHub; другие источники используют challenge или API-token. Универсального импорта произвольного документа нет.

`ProviderError(code, retryable, retryAfter)` не содержит токенов или исходного ответа. Допустимые основные ошибки: `source_unavailable`, `identity_not_found`, `reauthorization_required`, `invalid_source_response`, `rate_limited`, `invalid_identity`, `identity_mismatch`. Сервис сохраняет код, а интерфейс отображает понятное описание.

Официальный адаптер проверяет `snapshot.subject` и `snapshot.externalId` по сохранённому подключению. Кандидат не передаёт произвольный URL или самостоятельно назначенный внешний subject. Один subject одного провайдера может быть связан только с одним аккаунтом платформы.

## Идентичность ФСП и OIDC

У `fsp` используются настроенный issuer, discovery, JWKS и **RS256**. Проверяются подпись, issuer, audience, authorized party, expiration, issued-at, optional not-before и nonce. Затем `/v1/me` должен вернуть `subject`, равный `sub` ID token, и доверенный `fspId`. В базе связь хранится как `issuer#subject`; ручное поле FSP ID анкеты не участвует в проверке и не даёт подтверждения.

Поддерживается `client_secret_post` и обновление access token через refresh token. Повернутый refresh token сохраняется до следующего ресурсного запроса. Нет refresh token при истечении access token — требуется повторное подключение. В первой версии повторное подключение выполняется через отключение и новое подключение.

Discovery endpoints должны находиться на том же origin, что issuer. Это намеренное ограничение адаптера; при реальном контракте с разными доверенными origin список нужно явно согласовать и расширить. Redirects HTTP-клиента запрещены. Запросы идут только к операторским URL; HTTPS обязателен, loopback HTTP разрешён вне production для локальной разработки. Тайм-аут запроса — 10 секунд, ответ — максимум 1 МБ.

State привязан к текущему владельцу, живёт 10 минут, хранится хешем и расходуется один раз. PKCE verifier и nonce зашифрованы. Попытка завершить подключение из другого аккаунта не расходует чужой state.

Cookie существующей платформы имеют `SameSite=Strict`. Поэтому GET callback возвращает небольшую HTML-страницу: она удаляет query с кодом из адреса, выполняет same-origin POST с cookie, затем возвращает кандидата в профиль. Страница имеет `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, CSP с nonce и не использует внешние ресурсы. Proxy перед приложением должен исключать code/state из access-логов. Если используется отдельный домен API, потребуется отдельно согласованный browser-flow; текущая реализация рассчитана на same-origin frontend и API.

## Хранение и жизненный цикл

В SQLite основного сервера добавлены:

| Таблица | Назначение |
| --- | --- |
| `integration_connections` | Владелец, источник, внешний аккаунт, проверка принадлежности, зашифрованные credentials, согласие и состояние |
| `integration_pending` | Одноразовое незавершённое подключение, срок действия и зашифрованные verifier/nonce |
| `integration_evidence` | Нормализованное доказательство, статус, срок свежести, отпечаток исходной записи |
| `integration_jobs` | Очередь, попытки, результат и безопасный код ошибки |
| `integration_events` | ID и отпечаток обработанного подписанного события |

Токены шифруются AES-256-GCM с новым IV каждой записи. Ключ задаётся `INTEGRATION_ENCRYPTION_KEY`: **64 шестнадцатеричных символа / 32 байта**. Секреты и полные исходные внешние ответы не выдаются API. В development без операторского ключа создаётся файл `<ASSESSMENT_DB>.integrations.key` с правами 0600; он исключён из Git. Файл необходим для расшифровки после перезапуска и должен сохраняться рядом с базой. В `:memory:` используется временный ключ. Реальный `fsp` требует явно заданный операторский ключ.

Отключение доступно и после потери конфигурации источника. Удаление подключения немедленно удаляет локальные credentials, доказательства и pending state. Активные задачи становятся `cancelled`; поздний ответ не может восстановить данные. Удаление состояния платформы и отзыв сохранённого согласия также очищают подключения. Отключение не гарантирует удалённый отзыв access/refresh token в ФСП — такой метод нужно согласовать с провайдером; собственные данные платформы после отключения больше не обновляются.

Завершённые задачи сохраняются 30 дней, активные — до завершения. Достижения хранятся до отключения или удаления кабинета. Отозванные достижения сохраняются с соответствующей пометкой для объяснения истории. ID webhook-событий сохраняются без автоматического срока удаления для предотвращения повторной обработки. Очистка истёкших pending state и задач выполняется раз в минуту.

## Очередь и обновления

Worker работает в процессе Node.js, по одной задаче за раз. Созданная задача сохраняется до выполнения. Повтор sync при queued/running возвращает тот же ID. После перезапуска running-задачи возвращаются в очередь с сохранённым числом попыток. На одну задачу максимум три попытки. Для временных ошибок — задержки 1 и 2 секунды; `Retry-After` в секундах учитывается с максимумом 60 секунд. Ошибки идентичности и формата не повторяются.

Автоматическое обновление выполняется примерно раз в сутки с минутным шагом планировщика, начиная с последней попытки. `reauthorization_required` автоматически не повторяется. Запуск несколько раз в сутки вручную допускается в пределах rate limit. При ошибке сохраняется последний успешный снимок и дата его проверки; его эффективный статус становится `stale`, и он не даёт бонус ФСП до успешного обновления.

Свежесть доказательства — 7 суток от успешной проверки. По истечении оно становится `stale`. Ежеминутный tick обновляет индекс; возможна задержка исчезновения из фильтра до минуты. Публичный endpoint доказательств проверяет срок при каждом чтении. Отсутствие истории и отсутствие данных из-за ошибки — разные результаты. Успешный пустой снимок отзывает предыдущие активные доказательства.

Снимок ограничен 20 страницами / 2000 достижениями, по 100 записей на страницу. Повторяющийся cursor, дублированный ID, несовпадение владельца, превышение лимита или неверная запись приводят к отказу всего обновления. Стабильный локальный ID строится из ID подключения и ID записи источника. Источник должен обеспечивать согласованную пагинацию полного снимка.

**Ограничение:** очередь рассчитана на один экземпляр основного Node.js backend. Для нескольких процессов потребуется lease/claim в общей БД или выделенный worker. Шифрование не заменяет защищённое хранение операторского ключа. Эти ограничения не скрываются за заявлением готовности внешней интеграции.

## Что считается подтверждением

| Статус | Значение | Фильтр/бонус ФСП |
| --- | --- | --- |
| `verified` | Доверенный live-источник, проверенный владелец, активная свежая запись | Да, для провайдера `fsp` |
| `demo` | Вымышленный источник внутри общего сервиса интеграций | Не создаёт реальное подтверждение; HTTP-демосценарий описан отдельно |
| `unverified` | Принадлежность не подтверждена | Нет |
| `stale` | Проверка устарела или подключение требует обновления | Нет |
| `revoked` | Источник отозвал запись или она отсутствует в полном новом снимке | Нет |

Синтетические стартовые кандидаты и [сессионный демоисточник](fsp_integration.md) сохраняют учебную фильтрацию и ограниченный бонус с явной пометкой демо; это не проверка реальной личности или достижения. Сервер отдельно учитывает свежие доверенные записи провайдера `fsp` и активные одобренные заявки из пилотного PDF ФСП. Общие публичные результаты, Codeforces, AtCoder, Kaggle и GitHub автоматически не становятся достижениями ФСП. Один доверенный resolver связывает фильтр, ограниченное ранжирование внутри категории и объяснение источника. Грейд и исходные нейронные оценки интеграции не меняют.

Правила `fsp-discipline-v1`:

- `algorithms` → «Алгоритмы», «Структуры данных»;
- `cybersecurity` → «Информационная безопасность»;
- `data_analysis` → «Анализ данных»;
- неизвестная дисциплина → достижение без автоматически выведенных навыков.

Это свидетельства по направлениям, а не доказательство полного профессионального стека. Индивидуальные записи имеют scope `individual_result`; командные — `team_result`. Командный результат не подтверждает индивидуальное владение всеми компетенциями. Грейд не присваивается и не повышается интеграцией: его по-прежнему определяет серверный тест. LLM не устанавливает подлинность источника.

## Демонстрация без доступа к ФСП

Сессионный `fsp-demo` доступен только вне production и при `INTEGRATION_DEMO!=0`. В основном интерфейсе предусмотрены `achievements`, `empty` и `revoked`. Внутренний провайдер общего сервиса дополнительно содержит `not-found` и `unavailable` для изолированных проверок; это не дополнительные варианты основного HTTP-контракта. Все ID и названия явно демонстрационные; `identityVerified=false`. Данные не становятся `verified` даже после успешной синхронизации.

Запустите `npm run dev`, войдите кандидатом, сохраните согласие и откройте профиль. В разделе ФСП нажмите «Привязать ФСП», выберите сценарий и подтвердите загрузку вымышленных записей. Можно обновить данные, перезагрузить страницу и отвязать подключение. Этот путь не обращается к внешнему сервису; запросы и ошибки описаны в [контракте демопривязки](fsp_integration.md).

## Конфигурация реального провайдера

Все параметры задаются в `.env` основного сервера:

```dotenv
INTEGRATION_DEMO=0
INTEGRATION_ENCRYPTION_KEY=<64-hex-characters>
FSP_OIDC_ISSUER=https://<trusted-issuer>
FSP_CLIENT_ID=<registered-client>
FSP_CLIENT_SECRET=<client-secret>
FSP_API_BASE_URL=https://<agreed-resource-api>
FSP_REDIRECT_URI=https://<our-origin>/api/integrations/fsp/callback
FSP_WEBHOOK_SECRET=<optional-shared-webhook-secret>
```

Для production используйте HTTPS и `COOKIE_SECURE=1`. В development callback может быть `http://127.0.0.1:5173/api/integrations/fsp/callback` через proxy Vite. Все обязательные параметры, включая ключ, нужны для enabled=true. `APP_ENV=production` **или** `NODE_ENV=production` отключает демо и запрещает loopback HTTP.

Перед активацией согласовать с ФСП: issuer/discovery, client и callback; scopes; разрешённые алгоритмы и способ client authentication; `/v1/me` и принадлежность FSP ID; полный ресурсный снимок, пагинацию и стабильные ID; дисциплины, индивидуальную/командную атрибуцию, отзывы; лимиты и частоту обновлений; webhook при наличии. Получение официальных адресов и credentials остаётся внешней зависимостью. Автоматическое enabled=true означает полноту конфигурации, а не факт договорённости или проведённую проверку реального сервиса.

## Webhook

`POST /api/integrations/fsp/webhook` принимает `achievements.changed` и `identity.revoked`. Для последнего немедленно удаляются локальные токены, отменяются активные задачи и отзываются доказательства. Первое событие ставит обновление в очередь с проверкой сохранённого согласия.

```json
{
  "id": "event-unique-id",
  "type": "achievements.changed",
  "subject": "oidc-subject",
  "fspId": "participant-id"
}
```

Заголовки: `X-Integration-Timestamp` — UNIX seconds, `X-Integration-Signature` — `v1=<lowercase hex>`. Подпись: `HMAC-SHA256(FSP_WEBHOOK_SECRET, timestamp + "." + exactRawBody)`. Допуск времени ±300 секунд. При повторе ID с другими байтами тела — 409. Проверка подписи предшествует разбору JSON. Ответ для известного и неизвестного участника одинаковый: `202 {"status":"accepted"}`. Это подтверждает приём события, а не успешное обновление.

## Проверки

`npm run test:server` включает тесты интеграций: права и владение задачами, state и OIDC-подпись, PKCE, сопоставление личности, refresh rotation, пагинацию, ошибки и атомарность, свежесть, отзыв, внутренний демопровайдер без реального подтверждения, зашифрованное хранение, перезапуск, disconnect во время загрузки и HMAC/replay. Браузерные проверки используют изолированные сервисы и вымышленные аккаунты без отправки внешних писем. Основной сессионный HTTP-путь демо отдельно проверяет `npm run test:fsp`; внутренние фикстуры общего демопровайдера не доказывают совместимость его контракта с этим маршрутом.

Полный контакт с настоящим ФСП не проверялся: адреса и доступ организатором не предоставлены. Проверки реального адаптера используют изолированные ответы по предложенному контракту, подписанный тестовый OIDC token и подставной HTTP transport.

Основания: [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html), [Keycloak: identity providers](https://www.keycloak.org/docs/latest/server_admin/index.html#_identity_broker), [продуктовые правила](business_rules.md#4-достижения-фсп).
## Другие источники

Реализован [адаптер Codeforces](codeforces-integration.md): официальный API рейтинга/истории выступлений/принятых решений и одноразовая проверка контроля над аккаунтом через Organization. Эти результаты отображаются как внешние подтверждения, но не включают признак/бонус ФСП и не заменяют оценку грейда.

Также реализованы [AtCoder, Kaggle и GitHub](external-achievements.md): публичная история Algorithm с кодом в Affiliation; позиции команды в public leaderboard по проверенному API-токену; публичное GitHub-портфолио через OAuth+PKCE. Контракты — OpenAPI 1.5.0. Ограниченные выборки не заявляются как полная история; исчезновение из выборки не доказывает отзыв самим источником. GitHub требует регистрации собственного OAuth-приложения и приватной конфигурации сервера.

Также реализован [сбор результатов из официальных таблиц и новостей](public-achievements.md): ICPC, новости ФСП, реестр адаптеров, долговечная очередь, поиск по имени/команде и привязка с отдельной проверкой состава. Это путь без внешней авторизации; автоматическое извлечение публикации не подтверждает её принадлежность кандидату.

# Новый банк для согласования

Версия `2026.10.10-research-v1`, 10 октября 2026 года. **165 самостоятельных задач по 33 областям компетенций: по 33 на каждый из пяти грейдов.** Охвачены все 14 специализаций и все 62 технологии из `shared/catalog.ts`, которые используются в анкете и фильтрах. Задача может подходить нескольким специализациям, но считается в размере корпуса один раз. Детальное покрытие каждой технологии по уровням показано отдельно: наличие технологии в банке ещё не означает готовый экзамен по ней на каждом грейде.

Это отдельный исследовательский корпус со статусом `pending-user-review`. `server/bank.mjs`, динамический пул и предыдущий `server/open-bank.mjs` сохранены. Действующий пользовательский тест и его генератор не подключены к новому корпусу. Подтверждение грейда по этим задачам выключено; замена будет отдельным этапом после просмотра пользователем.

## Что собрано

- [Источники](sources.md): учебные банки MIT, Exercism, PGExercises, SQL Academy, материалы Яндекса, практические курсы и лабораторные компаний/сообществ. Документация, учебные примеры, реальные банки и кейсы помечены раздельно. Всего 69 реестровых записей; число автоматически сверяется в отчёте.
- [Закрытый каталог](closed-catalog.md): 165 парных кейсов с 330 вопросами, по два вопроса с четырьмя вариантами на каждый кейс.
- [Таблица происхождения](source-table.md): виды материалов, количество связанных задач и ссылки отдельно для каждого кейса и вопроса.
- [Полный каталог](catalog.md): условия по компетенциям и грейдам, без эталонов.
- [Покрытие](coverage.md): специализации, технологии и форматы; нули оставлены видимыми.
- [15 случайных задач](samples.md): по три разных компетенции на каждый грейд. Выборка сохранена для обсуждения.
- [Серверный модуль](../../server/review-bank.mjs): условия, ожидаемый ход решения, предметные критерии, критические ошибки и ссылки на источники.

Условия и эталоны написаны как самостоятельные сценарии по найденным темам. Это **не дословная копия или массовый импорт чужих задач**. Источники не приписывают этим сценариям профессиональные грейды; распределение сделал автор корпуса и оно требует предметного согласования. Страницы с неполным чтением отмечены `index-only` или `search-index`, без заявления о проверенном содержимом. В частности, решения 18.650 на странице MIT отсутствуют, а Apple/FreeRTOS возвращают только индекс или нечитабельную оболочку.

## Принцип предварительной сложности

| Грейд | Что требуется | Как ограничиваем задачу |
| --- | --- | --- |
| Стажёр | Выполнить конкретное действие, расчёт или небольшой код; проверить результат и основные границы | Один локальный объект или процесс, все исходные данные заданы |
| Junior | Собрать законченное решение, обработать ошибки и объяснить поведение | Несколько связанных правил, известный инструмент/модель |
| Middle | Самостоятельно выбрать подход, сохранить инвариант и проверить ограничения | Зависимые данные, ресурсы, конкуренция либо несколько состояний |
| Senior | Найти причину сложного дефекта, доказать устойчивость или сравнить способы с измерением | Несколько взаимодействующих ограничений и отказных сценариев |
| Lead | Определить общий технический/предметный контракт, обосновать решение, переход и критерии допуска | Несколько систем/потребителей, долгий жизненный цикл или конфликт целей |

Lead не означает обязанность управлять людьми; для математики/ML это может быть принятие проверяемого решения по точности, данным и ресурсам. Один сложный алгоритм сам по себе не доказывает Lead. Время 10–40 минут — ориентир для отдельной задачи, не новая длина пользовательского экзамена. Действующие 120 секунд нельзя переносить на эти кейсы.

## Форматы и критерии

Есть код, SQL, расчёты с объяснением и развёрнутые кейсы. У каждой задачи отдельное условие своего уровня, цель, путь решения и как минимум три конкретных критерия. Эталоны приватны; сервер их хранит для последующего предметного просмотра, а CLI-каталог и случайная выборка не включают ответы. Код пока не исполняется, LLM-оценивание и пользовательские открытые попытки не добавлены.

Закрытый корпус `server/closed-review-bank.mjs` сохраняет матрицу **33 компетенции × 5 грейдов** открытого банка: 33 кейса / 66 закрытых вопросов на каждом грейде. Вопросы проверяют результат и отдельный шаг, ограничение или отказный сценарий решения. У каждого один верный ответ из четырёх, приватный ключ и объяснение. Варианты на старших уровнях включают похожие планы с конкретной ошибкой в инварианте. Порядок ответов воспроизводим, верные позиции распределены по A/B/C/D. Кейс считается одной семьёй; два вопроса одного кейса не являются независимыми психометрическими наблюдениями.

Закрытый вопрос проверяет распознавание решения, поэтому **равная матрица и исходная идея не означают доказанную равную сложность форматов**. Грейды остаются `editorial-estimate`, независимая предметная экспертиза и пилотирование не проведены. Исходное время открытого кейса сохранено как предварительный верхний ориентир; оно не откалибровано для выбора ответа. Действующий 120-секундный формат не подключён к этим кейсам.

## Источники и БД

У открытой задачи, закрытого кейса и каждого закрытого вопроса есть `sourceUrl` и `sourceRefs`. Ссылки содержат ID материала, URL, роль (`topic-reference` либо `technical-reference`), раздел/предел атрибуции, дату и состояние чтения. Для некоторых задач добавлены прямые страницы PostgreSQL, Python asyncio, React, scikit-learn и статья Microsoft Research о SRM. Остальные ссылки честно обозначают тематическую опору или каталог; они не заявлены как адрес конкретного заимствованного упражнения. Условия, distractors и распределение по грейдам авторские. Указание источника само по себе не подтверждает качество задачи.

`npm run import:review-bank` сохраняет корпус в локальной SQLite `server/data/assessment.sqlite` (или `ASSESSMENT_DB`). Это отдельные таблицы:

- `review_bank_entries`: 165 открытых задач, 165 закрытых кейсов и 330 отдельных закрытых вопросов; в каждой из 660 записей обязательный `source_url`, версия и приватный payload.
- `review_bank_sources`: реестр материалов с URL, издателем, типом и состоянием проверки.
- `review_bank_entry_sources`: все связи задания с материалами, ссылки и разделы. Внешние ключи исключают отсутствующие источники.

Импорт атомарный, повторный запуск не создаёт дубликаты; разные версии корпуса сохраняются отдельно. БД принудительно допускает только `pending-user-review` и `active=0`. Таблицы действующего банка и попыток не обновляются. Отдельного публичного API просмотра/прохождения нового банка пока нет. Для fresh checkout требуется повторить импорт; локальная SQLite находится в gitignore.

Критерии задают наблюдаемые свидетельства ответа, а не его длину. Путь решения — черновой ориентир; математически/предметно эквивалентные решения следует принимать после проверки. Автоматического общего проходного балла и сопоставления со старой шкалой нет.

## Контракт будущих вариантов

В каждой задаче сохранены `intent`, `solutionPath`, предметные критерии и `generationContract`. Будущий генератор должен сохранить проверяемую идею, ход рассуждения и требования к сложности, но переписать не меньше трёх содержательных измерений: предметную ситуацию и участников, представление данных, форму вопроса и несущественные ограничения. Цифры и имена сами по себе не являются содержательным изменением.

Запрещены варианты, меняющие только числа/имена, перефразирующие тот же кейс, раскрывающие решение в условии или упрощающие исходное рассуждение. Каждый критерий должен быть заново привязан к новому условию; вариант нужно независимо решить. Этот контракт пока **не меняет действующий LLM-генератор** и не выдаётся за работающую проверку смысловой новизны.

## Проверка и просмотр

```sh
npm run validate:review-bank
npm run report:review-bank
npm run sample:review-bank
npm run sample:review-bank -- Middle
npm run test:review-bank
npm run validate:closed-review-bank
npm run report:closed-review-bank
npm run import:review-bank
npm run stats:review-bank
```

Проверка обнаруживает пропуски специализаций, технологий и грейдов, отсутствующие источники/рубрики и точные или числовые дубли. Она не доказывает реальную сложность, независимость близких сценариев или соответствие профессиональному грейду. Следующий этап после просмотра — предметные исправления и эталонные ответы кандидатов, затем отдельная интеграция открытого теста, вариантного генератора и валидация результатов.

# Генерация новых кейсов по исходному замыслу

Реализован отдельный авторский генератор нового корпуса: [код](../../server/anchored-generator.mjs), [хранилище](../../server/anchored-variant-store.mjs), [сравнение сложности](../../server/variant-difficulty.mjs). Он принимает ID любой из 165 открытых задач или 165 закрытых кейсов. Один запрос создаёт один новый кейс целиком, включая два закрытых вопроса, если выбран закрытый формат.

Исходные кейсы этого корпуса — авторские сценарии по указанным материалам, а не дословно импортированные упражнения. Генератор сохраняет именно это происхождение. URL и роль источника наследуются от выбранного кейса на сервере; модель не может придумать ссылку или присвоить себе подтверждённый профессиональный грейд.

## Один запрос и существенное изменение

Сервер собирает доверенный паспорт: цель, путь решения, критерии, критические ошибки, навыки, формат, грейд, предварительное основание сложности и источники. Паспорт привязан к версии и SHA-256 снимка исходного кейса. Для закрытого формата сохраняются два решения, проверяемые его двумя вопросами. Требования самостоятельного построения решения из открытой пары автоматически не добавляются: это повысило бы сложность и поменяло проверяемое умение.

За **один вызов `llm.chat`** модель возвращает:

- новое самодостаточное условие и название;
- для закрытого формата — два вопроса, по четыре варианта, ключи, объяснения и разбор ошибки каждого дистрактора;
- полное эталонное решение;
- сопоставление каждого исходного критерия с новым требованием, точными цитатами условия и решения;
- перенос каждой критической ошибки и способ её обнаружить;
- минимум три изменения из `domain`, `representation`, `constraints`, `question`; представление данных и форма вопроса обязательны;
- обоснование сохранения пути решения, отсутствие новых предпосылок/удалённых операций и риски для независимой проверки.

Допустимые направления: представить журнал вместо агрегатов; предложить исправить ошибочный расчёт вместо прямого вопроса; заменить рабочий процесс, сохранив тот же инвариант; изменить второстепенное ограничение, сохранив необходимые шаги. Это инструкции для автора, а не доказательство, что любое такое преобразование сохраняет сложность.

У нового вызова `retries: 0`, `fallback: null`. Ошибка транспорта, JSON или проверки не вызывает ещё один запрос, автоматическое исправление или обращение ко второй модели. Ответ — JSON mode с обязательной локальной проверкой формы; поддержка provider-specific JSON Schema не предполагается. Число HTTP-вызовов проверяется на подменённом транспорте настоящего OpenRouter-клиента. Порядок вариантов перемешивается сервером с корректным переносом ключа и разборов дистракторов.

Сервер проверяет количество вопросов, варианты, критерии и критические ошибки, принадлежность цитат, отсутствие дополнительных полей/навыков/источников, явной подсказки ответа, слишком длинного правильного варианта, числового дубля и близкого текстового повтора. Подмена одних чисел отклоняется после нормализации чисел; близкая замена имён и пересказ отсекаются сравнением слов. Три изменения требуют разных настоящих цитат, а не только заявления модели.

**Это эвристики и проверка структуры.** Они не умеют доказывать математическую правильность, смысловую новизну и равенство сложности. Пересказ с полностью иной лексикой может пройти; цитата решения может содержать ошибку. Поэтому успешный результат называется `needs-review`, а его смысловая проверка — `not-independently-verified`.

## На чём основана сопоставимость

| Уровень свидетельства | Что установлено | Чего он не доказывает |
| --- | --- | --- |
| Доверенный исходный паспорт | Тот же заявленный грейд, формат, навыки, операции и количество проверяемых решений | Реальную сложность исходного кейса |
| Проверенный ответ модели | Полная карта критериев, решение и свидетельства изменений в тексте | Корректность решения и отсутствие смыслового упрощения |
| Независимый эксперт | Правильность исходного и нового решения, перенос рассуждения, предпосылки, объём работы, правдоподобие вариантов, существенность изменений | Частоту успешных ответов в целевой популяции |
| Зарегистрированный пилот | Совместимость среднего балла в выбранной популяции и заданном допуске | Профессиональную валидность грейда, одинаковую дискриминацию, время или качество всего экзамена |

Такое разделение следует смыслу альтернативных форм: одинаковые проверяемые умения, требования к содержанию и статистике, условия предъявления. Это основание проектирования, а не заявление, что наш корпус уже является набором эквивалентных форм. [NCME: alternate forms, alignment, construct equivalence](https://ncme.org/resources/professional-learning/glossary/).

Эксперт должен самостоятельно решить обе задачи, проверить границы/числа/код, сравнить зависимости шагов и необходимые знания. Для закрытого кейса дополнительно проверяется единственность ответа и правдоподобие всех неверных решений. Чеклист и письменное обоснование обязательны; принятие экспертом меняет статус на `reviewed`, **не на `active`**. Самооценка той же модели не считается независимой экспертизой. Для открытого формата `plausibleDistractors=true` означает, что формату не добавлены варианты ответа; это нужно отразить в обосновании.

## Реализованный пилот и пределы статистики

После экспертизы фиксируется неизменяемый план сравнения конкретного исходного и нового кейсов: снимки, грейд, формат, размер каждой группы, заранее выбранные страты. Один участник получает случайно только исходный или новый кейс; назначение хранится и повторно не меняется. Рандомизация сбалансирована блоками по два внутри страты. Система принимает псевдонимный SHA-256 участника, а не имя или контакт.

После регистрации нельзя переписать положительную экспертизу или размер выборки. Если обнаружена ошибка, эксперт может отклонить вариант: дальнейшие назначения прекращаются, положительный допуск по отчёту блокируется, уже собранные результаты сохраняются.

Сотрудник, проводящий пилот, обеспечивает сопоставимые условия, аудит рекрутирования и отсутствие знакомства с заданиями. «Тот же грейд» здесь означает целевую когорту из плана, а не грейд, уже доказанный этими же задачами. Способ отнесения участника к страте нужно определить независимо до назначения. API прохождения пилота для кандидатов и интерфейс слепого экспертного оценивания не добавлены; текущие CLI-команды предназначены для контролируемой авторской проверки. Ответы принимаются только для уже назначенного участника. Назначения без результата не заменяются автоматически и не считаются ошибками: неполный пилот не проходит.

Один кейс даёт один балл в `[0,1]`: доля двух верных закрытых ответов либо нормированный средний балл предметных критериев открытого ответа. Закрытые ответы проверяет сервер по зафиксированным ключам, открытые оценивает независимый эксперт по шкале 0–2 и передаёт критерии. Два вопроса одного кейса не увеличивают число независимых участников. Повторные результаты, другой грейд/формат и незарегистрированные страты отвергаются.

Предел совместимости выбран нами: **±0.10 среднего нормированного балла**, alpha `0.05`. Это предварительная бизнес-политика, не опубликованный норматив. Для закрытого формата речь идёт о разнице средних долей верных ответов; для открытого — о разнице нормированных баллов, не «проценте людей, прошедших экзамен».

Используется консервативный интервал из неравенства Хёффдинга для независимых ограниченных наблюдений. Для разницы двух средних сумма квадратов диапазонов весов равна `1/n_anchor + 1/n_variant`. Поправка по заранее заданным стратам ограничивает совокупную вероятность ошибки. Основание неравенства: [Hoeffding, 1963](https://www.tandfonline.com/doi/abs/10.1080/01621459.1963.10500830). Формула применения к нашему баллу — реализация проекта:

```text
d = mean_variant - mean_anchor
r = sqrt(0.5 * (1/n_anchor + 1/n_variant) * ln(2 * strata_count / 0.05))
interval = [max(-1, d-r), min(1, d+r)]
compatible = fixed_sample_complete AND interval entirely inside (-0.10, 0.10)
```

По умолчанию нужны 1000 участников на каждую версию в каждой страте. Для одной страты радиус около `0.0607`: наблюдаемая разница `0.01` даёт интервал примерно `[-0.0507,0.0707]` и совместима с допуском. При 200 участниках на версию даже нулевая разница обычно не даёт достаточно узкого интервала. Минимальный разрешённый план — 200, но это не обещание положительного решения. Большая выборка не исправляет неправильный дизайн, отбор участников или ошибки оценщика.

Ранний положительный результат запрещён до полного фиксированного размера. Нет замены реального baseline «ожидаемой сложностью», псевдонаблюдениями или старым правилом 12 ответов/±0.25. При недостатке данных возвращается `awaiting-sample`, при широком интервале `inconclusive`, при доказанном выходе за предел — `different`. Если заданы несколько страт, условие должно выполниться в каждой: одинаковые общие средние не скрывают противоположный сдвиг в подгруппах.

Отчёт всегда сохраняет `approvedForCertification: false`. Перед переносом в зачёт отдельно нужны профессиональная проверка исходного уровня, дискриминация/связь с независимым уровнем участника, анализ времени и итогового решения на экзамене, контроль утечек и мониторинг после запуска. Сохранение времени как ориентировочного значения паспорта не является калибровкой времени. Несколько последовательных новых экспериментов потребуют отдельной политики контроля ошибки; отчёт одного фиксированного плана не покрывает массовый отбор удачных вариантов.

## Хранение и доступ

`anchored_variants` хранит исходный паспорт, новый кейс, решение, сопоставления, хеши, модель, версию генератора и историю экспертизы. `anchored_variant_sources` сохраняет URL каждого источника и внешние ключи к реестру. Сохранение варианта и всех связей атомарно. Отказы генерации пишутся с кодами причин без ответа провайдера или ключа. `anchored_difficulty_plans` и `anchored_pilot_assignments` хранят план, назначения и единственный результат участника.

SQL ограничивает `active=0` для каждого варианта. Подключения к выборке `ItemBank`, зачётным попыткам и изменения старого генератора нет. Новый механизм доступен в основном Node.js API и CLI; дополнительный FastAPI не получает эти маршруты автоматически.

Авторские HTTP-маршруты требуют действующего серверного права модератора:

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /api/review-bank/variants/generate` | JSON только `{ "anchorId": "research-mc:statistics:Middle" }`; 201 — черновик, 422 — отклонён, 503 — ошибка/нет ключа |
| `GET /api/review-bank/variants` | Список, фильтры `anchorId`, `grade`, состояние генератора |
| `GET /api/review-bank/variants/:id` | Приватный кейс с ключами, решением и источниками |
| `POST /api/review-bank/variants/:id/review` | Независимая экспертиза: `decision`, `checks`, `rationale` |

Генерация ограничена одним одновременным запуском на процесс и 10 запросами в час на аккаунт. Полностью новый путь решения не включён: для него нет исходного договора сопоставимости, потребуется новая семья и независимый baseline. Изменения данных/постановки в рамках исходного пути уже поддерживаются.

## Запуск

В серверном `.env` нужен `OPENROUTER_API_KEY`; модель берётся из `OPENROUTER_MODEL` либо прежнего Qwen по умолчанию. В окружении проверки ключ отсутствовал: тесты используют явно обозначенные авторские фикстуры и тестовый транспорт, реальный ответ модели и его предметное качество не заявляются как проверенные. Ключ в чат или Git передавать не нужно.

```sh
npm run variants:passport -- research-mc:statistics:Middle
npm run variants:generate -- research-mc:statistics:Middle /tmp/variant-private.json
npm run variants:generate -- research:sql:Senior /tmp/sql-private.json
npm run variants:list
npm run test:variants
```

JSON-экспорты содержат решения и ключи, предназначены для эксперта и создаются с режимом 0600. `ASSESSMENT_DB` позволяет использовать отдельную SQLite. Рабочую БД в Git не добавляем. При первом сохранении варианта исходный корпус импортируется, если его ещё нет.

Пример файла независимой экспертизы (галочки выставляются после самостоятельного решения, не автоматически):

```json
{
  "decision": "accept",
  "checks": {
    "anchorCorrectAndGradeAppropriate": true,
    "solutionCorrect": true,
    "sameReasoning": true,
    "similarWorkload": true,
    "noNewPrerequisites": true,
    "plausibleDistractors": true,
    "substantiveRewrite": true
  },
  "rationale": "Здесь эксперт описывает собственную проверку решения, переноса операций, трудных границ и различий двух кейсов; минимум 60 символов."
}
```

```sh
VARIANT_REVIEWER=expert-login node scripts/anchored-variants.mjs review variant-UUID /tmp/review.json
VARIANT_REVIEWER=expert-login node scripts/anchored-variants.mjs plan variant-UUID /tmp/plan-options.json
node scripts/anchored-variants.mjs assign plan-UUID /tmp/participant.json
node scripts/anchored-variants.mjs record plan-UUID /tmp/outcome.json
node scripts/anchored-variants.mjs report plan-UUID
```

Форматы файлов:

- `plan-options.json`: `{ "samplePerArm": 1000, "strata": ["low", "medium", "high"] }`; пустой объект выбирает одну страту `all` и 1000 на версию.
- `participant.json`: `{ "participantHash": "64 hex characters", "stratum": "medium" }`; сначала назначение, затем предъявление **только** соответствующего кейса без ключей.
- закрытый `outcome.json`: `{ "participantHash": "64 hex characters", "answers": [0, 2], "elapsedMs": 180000 }`; индексы вариантов 0–3 в конкретном зафиксированном порядке.
- открытый `outcome.json`: `{ "participantHash": "64 hex characters", "criterionScores": [2, 1, 2], "elapsedMs": 900000 }`; порядок критериев паспорта, шкала 0–2, оценка эксперта.

CLI — доверенная административная поверхность с доступом к БД, не кандидатский API. Подтверждение чеклиста или ввод фиктивных результатов администратором технически возможны; достоверность экспертизы и пилота требует организационного аудита. Ни один такой ввод не включает задачу в зачёт автоматически.

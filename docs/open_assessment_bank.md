# Банк открытых задач

Собран отдельный авторский серверный корпус для подготовки открытого экзамена из [проекта](assessment_design.md): 14 специализаций, пять уровней, по 40 независимых семейств на направление. В каждой из четырёх групп — по 10 семейств; всего 560 семейств и 2800 условий выбранного грейда. Дополнены BusinessAnalysis, ProductManagement и Embedded; исправлены отсутствовавшие ссылки Fullstack на OWASP. **Банк имеет статус `author-draft`: независимая предметная экспертиза и калибровка ещё не проведены, подтверждение грейда по нему отключено.** Действующий тест с вариантами ответа продолжает использовать прежний банк.

## Что находится в записи

Семейство содержит исходную задачу с условиями, основную группу компетенций, формат ответа, язык кода или псевдокода, предметный разбор, допустимые альтернативы, критические ошибки и рубрику. У каждого грейда заданы дополнительные условия и ожидаемое действие. В новых направлениях предметные рубрики находятся внутри `levels[grade].criteria`; компилятор выбирает именно их. При отсутствии рубрики уровня использует общую рубрику семейства и явно отмечает `rubricOrigin: shared-family-requires-grade-review`. Старые 440 семейств пока требуют проверки применимости предметных критериев к каждому грейду; отдельный критерий глубины этой проверки не заменяет.

Уровни одной задачи относятся к одному семейству и не считаются независимыми вопросами. Перефразировка, название компании или другая фамилия также не создают новую задачу. Проверка точных дублей выполняется автоматически; смысловую независимость и применимость рубрик к каждому уровню ещё нужно проверить содержательно. Для задания с рубрикой уровня сервер передаёт его собственный ожидаемый разбор, а не семейный эталон Middle; отдельный `levels[grade].referenceAnswer` можно добавить для более подробного решения.

Компетенции соответствуют [матрице проекта](assessment_design.md). В каждом направлении есть задачи всех групп: рабочие случаи, диагностика, обоснование решения и проверка. Для технических ролей добавлены задания с кодом и псевдокодом. UXUI, бизнес-анализ и управление продуктом проверяются предметными разборами и решениями, обязательные алгоритмы им не назначаются.

## Источники и происхождение

В реестре каждого источника сохранены издатель, URL, дата обращения, назначение и способ проверки. `opened` означает успешное открытие страницы; `search-index` обозначает проверку по поисковому индексу и не выдаётся за прочтение всей страницы.

Используются первичные технические документы и публичные материалы компаний. Например, [хендбук Яндекса](https://contest.yandex.ru/tracks/algorithms/introduction/intro), [разбор процессов QA в Ozon Tech](https://habr.com/ru/companies/ozontech/articles/707092/) и [материал RWB о распределённых рейтлимитах](https://habr.com/ru/companies/rwb/articles/932050/). Техническая публикация компании является источником фактов, а не доказательством происхождения задачи из её собеседования.

Условия, ответы и рубрики написаны как самостоятельные сценарии; полные тексты чужих статей не копируются. Источники не объявляются общедоступными по разрешительной лицензии автоматически. Не заявляется, что собраны все реальные вопросы Яндекса, Ozon, WB или всех компаний и вакансий: в этой работе такой полный банк не подтверждён.

Проверка корпуса и технической механики:

```powershell
npm run test:open-bank
npm run validate:open-bank
```

Сохранение закрытого примера программы для просмотра разработчиком:

```powershell
npm run sample:open-bank -- ML Middle
```

Полный экспорт для последующей серверной загрузки или работы с моделью:

```powershell
npm run export:open-bank
```

Артефакты записываются в игнорируемый каталог `server/data/open-bank/`. Они содержат эталоны и рубрики, поэтому их нельзя переносить в `frontend/public`, отдавать кандидату или публиковать вместе с клиентскими файлами. Пример является авторским просмотром, не попыткой кандидата, не присваивает категорию и не создаёт запись в истории тестирования.

Авторский просмотр подбирает задачи по группам компетенций. Он пока не закрепляет состав форматов, предусмотренный проектом экзамена: число заданий с кодом в примере может меняться. Правило отбора практических задач вместе с оцениванием ещё нужно подключить в экзаменационном движке.

Проверка структуры подтверждает наличие полей, источников, различающихся условий уровней, покрытие и возможность составить разные формы без повторения семейств. Она не доказывает правильность каждой рубрики, равную реальную сложность, устойчивость к заучиванию или профессиональный грейд.

Расширенный конечный банк также можно выучить или передать. Открытая форма и объём сами по себе не доказывают защиту; содержательные проверки с известными исходными вопросами, новые условия внутри проверенных семейств и контроль повторного раскрытия ещё нужны.

## Что остаётся до рабочего открытого экзамена

Нужно проверить решения и альтернативы по предметным областям, убедиться, что обязательные критерии применимы к конкретному заданию каждого грейда, и разобрать близкие семейства. Далее — подготовить отдельные эталонные ответы кандидатов, проверить согласованность оценивания и сопоставимость банковского и персонализированного пути.

Рубрики относятся к отдельным семействам (`criterionScope: family-local`). В новых направлениях часть критериев имеет повторяемый `skillId` вида `BusinessAnalysis:A:elicitation`; схема не допускает ссылку на чужую специализацию или группу. Это авторское сопоставление, которое ещё нужно проверить по содержанию и достаточности независимых случаев. Упрощённому действию стажёра нельзя приписывать сложный навык только ради одинакового идентификатора. Совпадение локального имени критерия у разных задач не доказывает, что они проверяют один навык; простое усреднение этих оценок не вводится.

Банк ещё не подключён к пользовательскому экзамену. Подготовлен [адаптер Haiku через OpenRouter](openrouter_assessment.md) для проверки черновиков и ограниченного предварительного контекста. Серверное сохранение открытых ответов, проверенный оценщик, политика повторных попыток и адаптивное продолжение остаются отдельными шагами. Обработчик текущего теста не принимает код как оцениваемый ответ; редактор пока сохраняет локальный черновик.

Отбор в авторском просмотре использует только непоказанные семейства и завершается явной ошибкой при их нехватке. Основная форма содержит 20 задач, по пять на группу; гарантируется минимум пять практических случаев: один на каждую группу и дополнительный в закреплённой программой группе. В направлениях с большой долей SQL или прикладных артефактов практических задач может быть больше. Формат `code` всегда практический; предметные текстовые случаи классифицированы отдельно в [политике](../server/open-bank/policy.mjs). Схема требует достаточный практический запас для двух форм без повторов. Этот отбор не заменяет адаптивную политику. Для продолжения по одной недостаточно покрытой группе может потребоваться расширение её пула; повтор той же задачи нельзя считать новым независимым свидетельством.

Персонализация ограничена разрешёнными полями. Числа, порядок событий, сложность, ограничения ресурсов, ожидаемые действия и рубрика закреплены. Заявленный опыт и известное название компании не добавляют баллы и не подтверждают подлинность достижений; эта проверка остаётся отдельной задачей команды.
